# 路線圖

> 決定日期：2026-10-31。架構細節見 [arch2.md](arch2.md)。

## 1. 決定

| 項目 | 決定 |
| --- | --- |
| 架構 | 大廳、房間、規則三分離，採「第 2 層分離」：同一個 repo、三個獨立程式，只透過 `proto/` 的介面溝通，互不 import 對方的程式碼 |
| 大廳 | **自己寫的薄 Go 大廳**。第一個公開版本不需要好友、私訊，所以先不用 Nakama |
| 房間 | Go，每個房間一個 goroutine |
| 規則 | Node，`goban-engine`（OGS）加 OGS 估算器；無狀態 |
| 服務之間 | gRPC（大廳 ↔ 房間雙向、房間 → 規則） |
| 玩家連線 | WebSocket，大廳一條、房間一條，進房用入場券 |
| 前端 | Vue，圍棋棋盤用 `goban`（OGS） |
| 圍棋終局 | 數子法；系統自動判死子，雙方確認；有爭議就恢復對局（照正常輪次）；確認時限到視為同意 |

**不再繼續的方向**：

- **Colyseus**：對局搬到 Go 之後，它只剩連線管理與房間列表推送，也沒有好友功能，不值得多一種技術。
- **boardgame.io**：自由度最低、限制最多，已停止維護。
- **Nakama**：社群功能現成，但現在用不到。等第三個里程碑再評估（見第 4 節）。規格已寫好：`poc/nakama-lobby-go-room` 分支的 `docs/poc-nakama-lobby-go-room.md`。
- **NNGS、IGS、OGS 後端**：不能用或不適合直接用，NNGS 只當規格參考（見 [design-discussion.md](design-discussion.md) 5.7 節）。

## 2. 為什麼這樣排

- **大廳選誰已經不急**：採第 2 層分離後，房間服務、規則服務與 proto 介面不論大廳用誰都一樣。之後要換成 Nakama，只影響大廳。
- **不重複做三次大廳**：大廳只做一個最薄的版本，房間與規則一開始就做正式版。
- **風險最高的先做**：自動判死子（估算器尚未實測）、規則服務的 gRPC、超時判定才是真正不確定的地方，大廳反而最確定（`poc/go-lobby` 已驗證）。
- **最快能實際下一盤棋**：第一個里程碑完成就能完整下一盤圍棋。

## 3. 里程碑

### 里程碑 1：能完整下一盤圍棋

預估：每週 5～8 小時、AI 協助開發，約 2～4 週。

| 順序 | 工作 | 內容 |
| --- | --- | --- |
| 1 | proto 介面 | 大廳 ↔ 房間（`CreateRoom`、`ReserveSeat`、`ListRooms`、`GetRecord`、房間事件）、房間 → 規則（`apply`）；repo 結構照 arch2 2.1 節 |
| 2 | 規則服務 | 包住 `goban-engine`；估算器編成 WebAssembly 在 Node 載入；連續 pass 後自動判死子、計分；單元測試（提子、打劫、自殺、重放、計分） |
| 3 | 房間服務 | 房間 goroutine、閘道、送出佇列（沿用 `poc/go-lobby`）；驗證入場券；先寫紀錄再廣播；呼叫規則服務；終局確認流程；回報房間事件；用假大廳測試 |
| 4 | 大廳 | 從 `poc/go-lobby` 依第 2 層拆出：訪客登入、`who`、房間列表推送、邀局、呼叫 `CreateRoom`、簽發入場券、接收房間事件、對局摘要 |
| 5 | 前端 | 大廳畫面（玩家、房間、邀請）；對局畫面（`goban` 棋盤、先擺子、pass、認輸、終局確認） |
| 6 | 端對端測試 | 用程式模擬兩位玩家完成一局 |

驗收條件：

- [ ] Alice 從大廳邀請 Bob，Bob 接受，雙方用入場券進房。
- [ ] 在 19 路棋盤下完一局：提子、打劫正確，不合法的落子被拒絕。
- [ ] 雙方連續 pass 後，系統自動判死子並計分；雙方確認後定案。也測一次「不同意 → 恢復對局 → 再次 pass → 定案」。
- [ ] 認輸可以結束對局。
- [ ] 棋譜完整存在房間服務的資料庫；大廳只有摘要；可以查回整局棋譜。
- [ ] 局結束後雙方回到大廳，房間從列表消失。
- [ ] 三個服務各自獨立啟動；`lobby/` 與 `room/` 沒有互相 import。

這個里程碑**不做**：計時、悔棋、觀戰、斷線重連、開放房間、五子棋、帳號登入。

### 里程碑 2：對局功能補齊

| 功能 | 依據 |
| --- | --- |
| 計時：日式讀秒、延遲補償、依收到時間判超時 | arch2 3.3 節、設計討論第 9 節 |
| 悔棋：提議機制 | 設計討論第 8 節 |
| 觀戰與講評（講評只給觀戰者） | arch2 第 7 節 |
| 斷線重連：重連憑證、到場時限 | arch2 5.3 節、第 9 節 |
| 開放房間 | arch2 6.2 節 |
| 五子棋（驗證房間沒有寫死圍棋） | arch2 4.1 節 |
| 估算器準確度實測（附帶的分級測試局面） | arch2 第 10 節 |

### 里程碑 3：社群功能與大廳的再評估

需要好友、私訊、帳號時才開始。

1. 花**最多一週**依 `poc/nakama-lobby-go-room` 的規格做驗證，只看最大的風險：Nakama 的 Go 擴充引用 gRPC 套件時，能否和 Nakama 本身的版本相容；以及 Nakama 能否照同一份 proto 介面和房間服務溝通。
2. 通過：換成 Nakama 大廳，房間服務與規則服務不用改。
3. 不通過：在自己的 Go 大廳上補好友、私訊、登入。

## 4. 主要風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| OGS 估算器判死子不準，或無法在 Node 載入 | 自動判死子做不出來 | 里程碑 1 第 2 步最先處理；有雙方確認與恢復對局，判錯不會判錯勝負；最壞情況改用「提乾淨再結算」或接 KataGo |
| `goban-engine` 的資料格式與我們的動作紀錄對不上 | 規則服務要寫較多轉換 | 規則服務只對外暴露我們的格式，`goban-engine` 包在裡面 |
| 兩個服務之間的事件同步出錯 | 房間列表或玩家狀態錯誤 | 事件帶序號、可重送、定期對帳（arch2 5.2 節） |
| 之後真的要換 Nakama 卻接不上 | 社群功能要自己寫 | 里程碑 3 只花一週驗證，不通過就自己寫 |
