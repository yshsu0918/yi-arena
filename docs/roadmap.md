# 路線圖

> 決定日期：2026-10-31（2026-11-01 調整文件結構）。
> 功能與階段見 [feature-list.md](feature-list.md)，規格見 [spec_v1.md](spec_v1.md)，決定的理由見 [decisions.md](decisions.md)。

**目標**：做一個類似野狐的線上棋類平台，先做好圍棋，之後擴充五子棋等其他遊戲；大廳管理器自己掌握，新增遊戲時不必改動平台本身。

## 1. 技術決定

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 架構 | 大廳、房間、規則三個獨立服務，同一個 repo，只透過 `proto/` 的介面溝通 | [D-01](decisions.md#d-01) |
| 大廳 | 自己寫的薄 Go 大廳；需要社群功能時（M2）再評估 Nakama | [D-02](decisions.md#d-02)、[D-20](decisions.md#d-20) |
| 房間 | Go，每個房間一個 goroutine | [D-01](decisions.md#d-01) |
| 規則 | Node，`goban-engine`（OGS 開源的圍棋規則庫）加 OGS 的死子估算器；無狀態 | [D-04](decisions.md#d-04)、[D-05](decisions.md#d-05)、[D-17](decisions.md#d-17) |
| 服務之間 | gRPC | [D-03](decisions.md#d-03) |
| 玩家連線 | WebSocket，大廳一條、房間一條，進房用入場券 | [D-01](decisions.md#d-01) |
| 前端 | Vue，圍棋棋盤用 `goban`（OGS），先擺子、伺服器為準 | [D-14](decisions.md#d-14) |
| 圍棋終局 | 數子法；系統提出死子判斷，雙方可切換死子後同意；談不攏才恢復對局；協商失敗 3 次由系統判定（之後改用 KataGo） | [D-06](decisions.md#d-06)、[D-07](decisions.md#d-07)、[D-26](decisions.md#d-26) |
| 服務分工 | 遊戲知識只放在規則服務；大廳與房間不寫任何遊戲規則，加遊戲只加規則模組與棋盤元件 | [D-10](decisions.md#d-10)、[D-27](decisions.md#d-27) |
| 斷線與閒置 | 斷線 10 分鐘或輪到時 15 分鐘不動作判負；M1 用簡易註冊、不設訪客，正式帳號在 M2 | [D-25](decisions.md#d-25)、[D-30](decisions.md#d-30) |
| 里程碑 | 只分兩個：M1 對齊 NNGS 的對局功能（含簡易註冊），M2 社群與正式帳號；聯棋用獨立的規則模組 | [D-28](decisions.md#d-28)、[D-29](decisions.md#d-29)、[D-31](decisions.md#d-31) |

不採用的方案（Colyseus、boardgame.io、NNGS、IGS、OGS 後端）見 [D-02](decisions.md#d-02) 與 [D-16](decisions.md#d-16)。

## 2. 里程碑

| 里程碑 | 目標 |
| --- | --- |
| M1 | 對局功能與 NNGS 對齊：圍棋與五子棋，含簡易註冊 |
| M2 | 好友、社群、等級分、正式帳號（第三方登入） |
| 未來 | 已確定要做、順序未定（見 [feature-list.md](feature-list.md) 第 16 節，依難度排列） |

只分兩個里程碑（[D-31](decisions.md#d-31)）：原本的 M2（對齊 NNGS 的對局功能、簡易註冊）併入 M1，原本的 M3 改稱 M2。

### M1：對局功能與 NNGS 對齊

目標：**NNGS 有的對局功能都要有**（[D-28](decisions.md#d-28)），所有人用簡易註冊的帳號登入，不設訪客（[D-30](decisions.md#d-30)）。

**實作規格見 [spec_v2.md](spec_v2.md)**。核心部分（約局、下棋、終局、保底時限、重連、棋譜）已寫完；併入的功能（棋鐘、悔棋、觀戰、封盤續下等）列在 spec_v2 的「待補規格」，之後逐章補上。

M1 內部分兩段做，但不是兩個里程碑：先把核心做到能完整下一盤，再補齊 NNGS 的功能。

**第一段：核心（規格已寫完）**

| 順序 | 工作 | 內容 | 規格 |
| --- | --- | --- | --- |
| 1 | proto 介面 | 大廳 ↔ 房間、房間 → 規則、大廳 → 規則；repo 結構 | [2.2](spec_v1.md#22-程式碼分離)、[第 4 章](spec_v1.md#4-介面) |
| 2 | 規則服務 | 包住 `goban-engine`；加入五子棋模組（沿用三框架 PoC 的規則）；估算器編成 WebAssembly 在 Node 載入；通用階段；`ValidateSettings`；決定執色；確定性重放（不用隨機數）；提出死子判斷與目數、切換死子、系統判定；單元測試（提子、打劫、自殺、重放、計分、切換死子） | [第 6 章](spec_v1.md#6-規則服務) |
| 3 | 房間服務 | 房間 goroutine、閘道、送出佇列；驗證入場券；基本重連；先寫紀錄再廣播；呼叫規則服務；通用的「等待雙方同意」處理與協商失敗次數；保底時限（含閒置與斷線判負）；以 outbox 回報房間事件；用假大廳測試；同一份房間程式跑圍棋與五子棋 | [第 5 章](spec_v1.md#5-房間內部)、[3.3](spec_v1.md#33-入房與重連)、[3.6](spec_v1.md#36-時限與棋鐘) |

| 6 | 前端 | 註冊與登入頁；大廳畫面（玩家、房間、邀請）；五子棋棋盤元件；對局畫面（`goban` 棋盤、先擺子、pass、認輸、切換死子、同意、恢復對局）；重新整理後自動重連 | [3.4](spec_v1.md#34-對局)、[3.5](spec_v1.md#35-終局) |
| 7 | 端對端測試 | 用程式模擬兩位玩家完成一局 | — |

第二段要新增的通用機制（延續 [D-27](decisions.md#d-27)，不寫死圍棋）：

1. **提議與同意**（`offer{type}`）：悔棋、暫停、改貼目、封盤、和棋共用同一套流程。
2. **棋鐘模組**放在房間服務，讀秒方式由設定決定。
3. **觀戰者身分**：大廳簽發觀戰入場券；規則服務依身分回傳畫面。
4. **從棋譜還原對局**：封盤續下用動作紀錄重放回到原局面；房間服務重啟也可以改用這個機制還原，而不是中止。

**驗收條件（第一段）**：

- [ ] Alice 與 Bob 註冊並登入；Alice 從大廳邀請 Bob，Bob 接受，雙方用入場券進房。
- [ ] 在 19 路棋盤下完一局：提子、打劫正確，不合法的落子被拒絕。
- [ ] 雙方連續 pass 後，系統提出死子判斷並計分；雙方可點選切換死子，任一方修改後對方的同意作廢；雙方同意後定案。也測一次「談不攏 → 恢復對局 → 再次 pass → 定案」。
- [ ] 認輸可以結束對局。
- [ ] 棋譜完整存在房間服務的資料庫；大廳只有摘要；可以查回整局棋譜。
- [ ] 局結束後雙方回到大廳，房間從列表消失。
- [ ] 對局中重新整理頁面，能用重連憑證回到原座位與目前局面；換一台裝置登入同一個帳號，能用 `rejoin` 回到對局。
- [ ] 接受邀請後有人不進房、終局確認沒人回應、雙方都關掉分頁：房間都會在時限內結束，不留下殘留的房間或「對局中」狀態。
- [ ] 斷線 10 分鐘或輪到時 15 分鐘不動作會判負；點目協商失敗 3 次由系統判定。
- [ ] 下完一局五子棋（連五獲勝、下滿和局）；房間服務與大廳服務沒有為五子棋寫任何專屬的程式碼，只有規則服務多一個模組、前端多一個棋盤元件（[D-23](decisions.md#d-23)）。
- [ ] 各服務各自獨立啟動；`lobby/` 與 `room/` 沒有互相 import。

第二段的驗收條件隨各章規格補上。

M1 **不做**（都在 M2 或之後）：好友、私訊、離線訊息、封鎖、大廳聊天、聊天頻道、等級分與排行榜、天梯、第三方登入、個人資料與查詢玩家；聯棋、比賽、死活題；五子棋的連珠規則（禁手）；日本規則。

### M2：好友、社群、等級分、正式帳號

需要知道「你是誰」的功能都在這裡：

- **帳號**：把 M1 的簡易註冊換成正式的身分服務（第三方登入：微信、Google、Apple、Facebook 等，候選與考量見 [D-30](decisions.md#d-30)）；個人資料、查詢玩家。
- **社群**：好友與上線通知、私訊、離線訊息、封鎖、大廳聊天、聊天頻道。
- **等級分**：計分／不計分對局、等級分、段位、排行榜、讓子建議、天梯。

做法未定，取決於**主要市場**（台灣或海外、中國大陸），候選方案：

| 方案 | 說明 |
| --- | --- |
| 自己寫 | Go 社群服務，資料存 PostgreSQL；功能範圍不大，PoC 已寫過私訊與聊天 |
| Nakama | 帳號、好友、私訊現成；只用在帳號與社群，不必換掉整個大廳。依 [Nakama 驗證規格](https://github.com/yshsu0918/yi-arena/blob/poc/nakama-lobby-go-room/docs/poc-nakama-lobby-go-room.md) 花最多一週驗證 |
| XMPP 伺服器（ejabberd、Prosody） | 好友、上線狀態、私訊、離線訊息、封鎖、群聊幾乎一對一對應 NNGS 的社群指令 |
| 商用即時通訊服務 | 中國大陸可考慮騰訊雲 IM 等；連線與合規比較好處理，但按用量付費、被平台綁住 |

不論哪個方案，社群都可以做成和大廳分開的元件：大廳只在 `match` 時詢問「能不能邀請」（封鎖），其餘互不依賴。

## 3. 主要風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| OGS 估算器判死子不準，或無法在 Node 載入 | 自動判死子做不出來或常常要修正 | M1 第 2 步最先處理；雙方可手動切換死子，雙方同意的結果不受估算器影響；只有協商失敗 3 次由系統判定時才依估算器（D-26），這類局會標記供後台複查，之後改用 KataGo 判定；最壞情況改用「提乾淨再結算」或接 KataGo |
| 房間不小心寫死圍棋的流程 | 加其他遊戲時要改房間程式 | 階段與提案用通用格式；M1 就用同一份房間程式跑圍棋與五子棋 |
| `goban-engine` 的資料格式與動作紀錄對不上 | 規則服務要寫較多轉換 | 規則服務只對外暴露自己的格式，`goban-engine` 包在裡面 |
| 兩個服務之間的事件同步出錯 | 房間列表或玩家狀態錯誤 | 事件帶序號、可重送、定期對帳 |
| 帳號與社群的方案未定 | M2 開工時才發現要依市場重做 | M1 期間先確定主要市場，再選方案（見 M2） |
| 簡易註冊之後要換成正式的身分服務 | 帳號資料要搬移 | 介面一開始就照 OIDC token 設計，只認 `user_id`（D-30） |
