# 路線圖

> 決定日期：2026-10-31。架構細節見 [architecture_v1.md](architecture_v1.md)。

**目標**：做一個類似野狐的線上棋類平台，先做好圍棋，之後擴充五子棋等其他遊戲；大廳管理器自己掌握，新增遊戲時不必改動平台本身。

## 1. 決定

| 項目 | 決定 |
| --- | --- |
| 架構 | 大廳、房間、規則三分離，採「第 2 層分離」：同一個 repo、三個獨立程式，只透過 `proto/` 的介面溝通，互不 import 對方的程式碼 |
| 大廳 | **自己寫的薄 Go 大廳**。第一個公開版本不需要好友、私訊，所以先不用 Nakama |
| 房間 | Go，每個房間一個 goroutine |
| 規則 | Node，`goban-engine`（OGS 開源的圍棋規則庫）加 OGS 的死子估算器（終局時自動判斷死子）；無狀態 |
| 服務之間 | gRPC（大廳 ↔ 房間雙向、房間 → 規則） |
| 玩家連線 | WebSocket，大廳一條、房間一條，進房用入場券 |
| 前端 | Vue，圍棋棋盤用 `goban`（OGS） |
| 圍棋終局 | 數子法；系統自動提出死子判斷，雙方可手動切換死子後同意；談不攏才恢復對局（照正常輪次）；確認時限到視為同意 |

**不再繼續的方向**：

- **Colyseus**：對局搬到 Go 之後，它只剩連線管理與房間列表推送，也沒有好友功能，不值得多一種技術。
- **boardgame.io**：自由度最低、限制最多，已停止維護。
- **Nakama**：社群功能現成，但現在用不到。等里程碑 3 再評估（見第 3 節）。規格已寫好：[poc-nakama-lobby-go-room.md](https://github.com/yshsu0918/yi-arena/blob/poc/nakama-lobby-go-room/docs/poc-nakama-lobby-go-room.md)。
- **NNGS、IGS、OGS 後端**：不能用或不適合直接用，NNGS 只當規格參考（見 [design-discussion.md](design-discussion.md) 5.7 節）。

## 2. 為什麼這樣排

- **大廳選誰已經不急**：採第 2 層分離後，房間服務、規則服務與 proto 介面不論大廳用誰都一樣。之後要換成 Nakama，只影響大廳。
- **不重複做三次大廳**：大廳只做一個最薄的版本，房間與規則一開始就做正式版。
- **風險最高的先做**：自動判死子（估算器尚未實測）、規則服務的 gRPC、超時判定才是真正不確定的地方，大廳反而最確定：[Go 大廳 PoC](https://github.com/yshsu0918/yi-arena/blob/poc/go-lobby/docs/poc-go-lobby.md) 已驗證 goroutine 大廳與房間模型，100 位模擬使用者全數通過（當時大廳與房間在同一個程序，拆成獨立服務與 gRPC 是本里程碑要做的）。
- **最快能實際下一盤棋**：第一個里程碑完成就能完整下一盤圍棋。

## 3. 里程碑

### 里程碑 1：能完整下一盤圍棋

預估：每週 5～8 小時、AI 協助開發，約 3～5 週。

| 順序 | 工作 | 內容 |
| --- | --- | --- |
| 1 | proto 介面 | 大廳 ↔ 房間（`CreateRoom`、`ReserveSeat`、`ListRooms`、`GetRecord`、房間事件）、房間 → 規則（`apply`）；repo 結構照架構文件 2.1 節 |
| 2 | 規則服務 | 包住 `goban-engine`；估算器編成 WebAssembly 在 Node 載入；回傳通用階段（進行中、等待雙方同意、已結束）；連續 pass 後提出死子判斷與目數，支援切換死子；單元測試（提子、打劫、自殺、重放、計分、切換死子） |
| 3 | 房間服務 | 房間 goroutine、閘道、送出佇列（沿用 `poc/go-lobby`）；驗證入場券；基本重連（重連憑證）；先寫紀錄再廣播；呼叫規則服務；通用的「等待雙方同意」處理（不寫死圍棋）；保底時限：到場、確認、全員斷線；回報房間事件；用假大廳與假遊戲（例如連三子）測試 |
| 4 | 大廳 | 從 `poc/go-lobby` 依第 2 層拆出：訪客登入、`who`、房間列表推送、邀局、呼叫 `CreateRoom`、簽發入場券、接收房間事件、對局摘要 |
| 5 | 前端 | 大廳畫面（玩家、房間、邀請）；對局畫面（`goban` 棋盤、先擺子、pass、認輸、點選切換死子、同意、恢復對局）；重新整理後自動重連 |
| 6 | 端對端測試 | 用程式模擬兩位玩家完成一局 |

驗收條件：

- [ ] Alice 從大廳邀請 Bob，Bob 接受，雙方用入場券進房。
- [ ] 在 19 路棋盤下完一局：提子、打劫正確，不合法的落子被拒絕。
- [ ] 雙方連續 pass 後，系統自動提出死子判斷並計分；雙方可點選切換死子，任一方修改後對方的同意作廢；雙方同意後定案。也測一次「談不攏 → 恢復對局 → 再次 pass → 定案」。
- [ ] 認輸可以結束對局。
- [ ] 棋譜完整存在房間服務的資料庫；大廳只有摘要；可以查回整局棋譜。
- [ ] 局結束後雙方回到大廳，房間從列表消失。
- [ ] 對局中重新整理頁面，能用重連憑證回到原座位與目前局面。
- [ ] 接受邀請後有人不進房、終局確認沒人回應、雙方都關掉分頁：房間都會在時限內結束，不留下殘留的房間或「對局中」狀態。
- [ ] 房間服務的測試用一個假遊戲跑過，房間程式碼不含圍棋專屬的邏輯。
- [ ] 三個服務各自獨立啟動；`lobby/` 與 `room/` 沒有互相 import。

這個里程碑**不做**：棋鐘（日式讀秒、超時判負）、悔棋、觀戰、完整的斷線處理（保留座位倒數、跨裝置重連）、開放房間、五子棋、帳號登入。

注意：「不做棋鐘」不代表房間沒有時限。到場、終局確認、全員斷線三種保底時限要做，否則房間可能永遠不結束（見架構文件 3.6 節）。

### 里程碑 3：社群功能與大廳的再評估

需要好友、私訊、帳號時才開始。

1. 花**最多一週**依 [Nakama 驗證規格](https://github.com/yshsu0918/yi-arena/blob/poc/nakama-lobby-go-room/docs/poc-nakama-lobby-go-room.md) 做驗證，只看最大的風險：Nakama 的 Go 擴充引用 gRPC 套件時，能否和 Nakama 本身的版本相容；以及 Nakama 能否照同一份 proto 介面和房間服務溝通。
2. 通過：換成 Nakama 大廳，房間服務與規則服務不用改。
3. 不通過：在自己的 Go 大廳上補好友、私訊、登入。

## 4. 主要風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| OGS 估算器判死子不準，或無法在 Node 載入 | 自動判死子做不出來或常常要修正 | 里程碑 1 第 2 步最先處理；雙方可手動切換死子，判錯不會判錯勝負；最壞情況改用「提乾淨再結算」或接 KataGo |
| 房間不小心寫死圍棋的流程 | 加五子棋等遊戲時要改房間程式 | 階段與提案用通用格式（架構文件 4.2 節）；房間服務測試用假遊戲跑過 |
| `goban-engine` 的資料格式與我們的動作紀錄對不上 | 規則服務要寫較多轉換 | 規則服務只對外暴露我們的格式，`goban-engine` 包在裡面 |
| 兩個服務之間的事件同步出錯 | 房間列表或玩家狀態錯誤 | 事件帶序號、可重送、定期對帳（架構文件 5.2 節） |
| 之後真的要換 Nakama 卻接不上 | 社群功能要自己寫 | 里程碑 3 只花一週驗證，不通過就自己寫 |
