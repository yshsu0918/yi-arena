# 路線圖

> 功能清單見 [feature-list.md](feature-list.md)，實作規格見 [spec_v2.md](spec_v2.md)，決定的理由見 [decisions.md](decisions.md)。
> 只分兩類：**現在要做**（第 2 節，規格全部在 spec_v2）與**未來要做**（第 3 節）。

**目標**：做一個類似野狐的線上棋類平台，先做好圍棋，同時支援五子棋證明能擴充其他遊戲；大廳管理器自己掌握，新增遊戲時不必改動平台本身；NNGS 有的對局功能都要有。

## 1. 技術決定

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 架構 | 身分、大廳、房間、規則、棋譜五個獨立服務，同一個 repo，只透過 `proto/` 的介面溝通，各自的資料庫 | [D-01](decisions.md#d-01)、[D-33](decisions.md#d-33) |
| 大廳 | 自己寫的薄 Go 大廳；做社群功能時再評估 Nakama | [D-02](decisions.md#d-02)、[D-20](decisions.md#d-20) |
| 房間 | Go，每個房間一個 goroutine | [D-01](decisions.md#d-01) |
| 規則 | Node，`goban-engine`（OGS 開源的圍棋規則庫）加 OGS 的死子估算器；無狀態 | [D-04](decisions.md#d-04)、[D-05](decisions.md#d-05)、[D-17](decisions.md#d-17) |
| 服務分工 | 遊戲知識只放在規則服務；大廳與房間不寫任何遊戲規則，加遊戲只加規則模組與棋盤元件 | [D-10](decisions.md#d-10)、[D-27](decisions.md#d-27) |
| 棋譜 | 進行中的局在房間服務；對局結束後交給棋譜服務，負責查詢、SGF、戰績 | [D-33](decisions.md#d-33) |
| 帳號 | 簡易註冊（名稱加密碼），不設訪客；之後換成正式的身分服務 | [D-30](decisions.md#d-30) |
| 服務之間 | gRPC | [D-03](decisions.md#d-03) |
| 玩家連線 | WebSocket，大廳一條、房間一條，進房用入場券 | [D-01](decisions.md#d-01) |
| 前端 | Vue，圍棋棋盤用 `goban`（OGS），先擺子、伺服器為準 | [D-14](decisions.md#d-14) |
| 圍棋終局 | 數子法；系統提出死子判斷，雙方可切換死子後同意；談不攏才恢復對局；協商失敗 3 次由系統判定（之後改用 KataGo） | [D-06](decisions.md#d-06)、[D-07](decisions.md#d-07)、[D-26](decisions.md#d-26) |
| 斷線與閒置 | 斷線 10 分鐘或輪到時 15 分鐘不動作判負 | [D-25](decisions.md#d-25) |
| 範圍 | 現在要做：NNGS 的對局功能；未來要做：社群、等級分、正式帳號等 | [D-28](decisions.md#d-28)、[D-31](decisions.md#d-31) |

不採用的方案（Colyseus、boardgame.io、NNGS、IGS、OGS 後端）見 [D-02](decisions.md#d-02) 與 [D-16](decisions.md#d-16)。

## 2. 現在要做

規格全部在 [spec_v2.md](spec_v2.md)，功能總表見 [spec_v2 1.1 節](spec_v2.md#11-現在要做)。

### 2.1 實作順序

前 8 步做完就能完整下一盤圍棋與五子棋，適合當作第一次展示的檢查點；之後依序補齊其他功能。這只是建議的順序，不是不同的階段。

| 順序 | 工作 | 內容 | 規格（spec_v2） |
| --- | --- | --- | --- |
| 1 | proto 介面與 repo | 各服務之間的介面；目錄結構 | [第 2 章](spec_v2.md#2-系統組成)、[第 5 章](spec_v2.md#5-介面) |
| 2 | 規則服務 | 包住 `goban-engine`；五子棋模組（沿用三框架 PoC 的規則）；估算器編成 WebAssembly 在 Node 載入；`ValidateSettings`；決定執色；確定性重放；死子提案、切換死子、系統判定；單元測試 | [第 7 章](spec_v2.md#7-規則服務) |
| 3 | 房間服務 | 房間 goroutine、閘道、送出佇列；入場券與重連；先寫紀錄再廣播；等待雙方同意與協商失敗次數；保底時限；棋鐘（加拿大讀秒、日式讀秒、每手限時、加秒制、延遲補償、超時判定、送時間）；outbox；同一份程式跑圍棋與五子棋 | [第 6 章](spec_v2.md#6-房間的階段與指令)、[4.6](spec_v2.md#46-保底時限)、[12.3](spec_v2.md#123-棋鐘) |
| 4 | 棋譜服務 | 接收對局結束時的完整棋譜；查棋譜、SGF、戰績 | [4.8](spec_v2.md#48-棋譜與戰績)、[5.6](spec_v2.md#56-棋譜服務d-33) |
| 5 | 身分服務 | 簡易註冊、登入、改密碼，發帶 `user_id` 的 token | [4.11](spec_v2.md#411-簡易註冊與登入身分服務) |
| 6 | 大廳 | 驗證 token、`who`、房間列表、約局（`match`、`accept`、`decline`、`withdraw`、`pending`）、多房間、`rejoin`、建房、入場券、房間事件 | [4.1](spec_v2.md#41-登入與大廳)、[4.2](spec_v2.md#42-約局)、[4.3](spec_v2.md#43-建房與入房) |
| 7 | 前端 | 註冊與登入頁；大廳畫面；圍棋與五子棋的對局畫面（先擺子、pass、認輸、點目、棋鐘倒數）；自動重連 | [4.4](spec_v2.md#44-對局)、[4.5](spec_v2.md#45-圍棋終局) |
| 8 | 端對端測試 | 用程式模擬兩位玩家完成一局（**檢查點：能完整下一盤**） | [第 11 章](spec_v2.md#11-驗收條件) |
| 9 | 提議與同意 | 通用的提議流程；悔棋、改貼目、和棋、暫停 | [12.2](spec_v2.md#122-提議與同意)、[12.6](spec_v2.md#126-悔棋改貼目和棋) |
| 10 | 約局補充與開放房間 | 還價、`open` 開關、忙碌訊息、讓子；`seek`、`join` | [12.4](spec_v2.md#124-約局補充)、[12.5](spec_v2.md#125-開放房間) |
| 11 | 觀戰 | 觀戰入場券、講評、觀戰者列表、同時看多局；壓力測試 A、B | [12.7](spec_v2.md#127-觀戰與講評)、[load-test-plan.md](load-test-plan.md) |
| 12 | 封盤與續下 | 封盤（以 `adjourned` 結束）；`stored`、`look`、`sresign`（棋譜服務）；`load` 開新房續下（`go_resume`）；房間服務重啟時未完成的局自動封盤 | [12.8](spec_v2.md#128-封盤與續下) |
| 13 | 棋譜工具 | 匯出 SGF、網頁覆盤、覆盤房間（`go_review`） | [12.9](spec_v2.md#129-棋譜工具) |
| 14 | 斷線補充、玩家與管理 | 保留座位倒數；查詢玩家、看別人的戰績；伺服器資訊、公告；管理員頁面、禁言、踢人、封鎖、管理紀錄 | [12.10](spec_v2.md#1210-斷線補充)、[12.11](spec_v2.md#1211-大廳資訊與管理) |
| 15 | 驗證 | 估算器準確度實測 | [decisions.md 待驗證](decisions.md#待驗證) |

### 2.2 驗收條件

完整的驗收條件見 [spec_v2 第 11 章](spec_v2.md#11-驗收條件)與 [12.14 節](spec_v2.md#1214-驗收條件)。重點：

- [ ] 兩位玩家註冊登入、約局、用入場券進房，下完一局 19 路圍棋與一局五子棋；提子、打劫、點目、系統判定都正確。
- [ ] 棋鐘正確（圍棋預設加拿大讀秒、五子棋預設每手限時），截止前收到的一手不算超時；斷線 10 分鐘或閒置 15 分鐘判負。
- [ ] 重新整理或換裝置都能回到對局；房間服務重啟後進行中的局會封盤，之後可以續下。
- [ ] 對局結束後棋譜服務有完整棋譜、SGF 與雙方的戰績；可以查別人的戰績。
- [ ] 悔棋、改貼目、和棋、暫停、封盤續下、還價、開放房間、觀戰與講評、覆盤房間、管理功能都能使用。
- [ ] 房間服務與大廳服務沒有任何遊戲專屬的程式碼：五子棋與覆盤房間都只是規則服務多一個模組、前端多一個畫面（D-23、D-27、D-34）。
- [ ] 各服務各自獨立啟動，互不 import。

## 3. 未來要做

不在現在的規格內。

### 3.1 優先：需要正式帳號的功能

- **正式帳號**：把簡易註冊換成正式的身分服務，支援第三方登入（微信、Google、Apple、Facebook 等，候選與考量見 [D-30](decisions.md#d-30)）；個人資料（自我介紹、頭像）。
- **社群**：好友與上線通知、私訊、離線訊息、封鎖、大廳聊天、聊天頻道。
- **等級分**：計分對局、等級分、段位、排行榜、讓子建議、天梯。

做法取決於**主要市場**（台灣或海外、中國大陸，尚未決定），候選方案：

| 方案 | 說明 |
| --- | --- |
| 自己寫 | Go 社群服務，資料存 PostgreSQL；功能範圍不大，PoC 已寫過私訊與聊天 |
| Nakama | 帳號、好友、私訊現成；只用在帳號與社群，不必換掉整個大廳。依 [Nakama 驗證規格](https://github.com/yshsu0918/yi-arena/blob/poc/nakama-lobby-go-room/docs/poc-nakama-lobby-go-room.md) 花最多一週驗證 |
| XMPP 伺服器（ejabberd、Prosody） | 好友、上線狀態、私訊、離線訊息、封鎖、群聊幾乎一對一對應 NNGS 的社群指令 |
| 商用即時通訊服務 | 中國大陸可考慮騰訊雲 IM 等；連線與合規比較好處理，但按用量付費、被平台綁住 |

不論哪個方案，社群都可以做成和大廳分開的元件：大廳只在 `match` 時詢問「能不能邀請」（封鎖），其餘互不依賴。

### 3.2 之後

聯棋（獨立的規則模組，[D-29](decisions.md#d-29)）、比賽與錦標賽、死活題、AI 形勢判斷與對手（KataGo，也用於系統判定）、大量觀戰（直播模式）、延遲直播、自動配對、檢舉與防作弊偵測、五子棋的連珠規則（禁手）等。完整清單見 [feature-list.md](feature-list.md) 第 16 節（依難度排列）。

## 4. 主要風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| OGS 估算器判死子不準，或無法在 Node 載入 | 自動判死子做不出來或常常要修正 | 實作順序第 2 步最先處理；雙方可手動切換死子，雙方同意的結果不受估算器影響；只有協商失敗 3 次由系統判定時才依估算器（D-26），這類局會標記供後台複查，之後改用 KataGo 判定；最壞情況改用「提乾淨再結算」或接 KataGo |
| 房間不小心寫死圍棋的流程 | 加其他遊戲時要改房間程式 | 階段與提案用通用格式；同一份房間程式跑圍棋、五子棋與覆盤房間 |
| `goban-engine` 的資料格式與動作紀錄對不上 | 規則服務要寫較多轉換 | 規則服務只對外暴露自己的格式，`goban-engine` 包在裡面 |
| 服務之間的事件同步出錯 | 房間列表、玩家狀態或戰績錯誤 | outbox 先存再送、事件帶序號可重送、定期對帳 |
| 範圍大，要做完才完整 | 很久才有東西可以展示 | 實作順序第 8 步是「能完整下一盤」的檢查點，可以先展示 |
| 帳號與社群的方案未定 | 開始做社群時才發現要依市場重做 | 現在就先確定主要市場，再選方案（見 3.1 節） |
| 簡易註冊之後要換成正式的身分服務 | 帳號資料要搬移 | 介面一開始就照 OIDC token 設計，只認 `user_id`（D-30） |
