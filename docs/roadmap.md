# 路線圖

> 決定日期：2026-10-31（2026-11-01 調整文件結構）。
> 功能與階段見 [feature-list.md](feature-list.md)，規格見 [spec_v1.md](spec_v1.md)，決定的理由見 [decisions.md](decisions.md)。

**目標**：做一個類似野狐的線上棋類平台，先做好圍棋，之後擴充五子棋等其他遊戲；大廳管理器自己掌握，新增遊戲時不必改動平台本身。

## 1. 技術決定

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 架構 | 大廳、房間、規則三個獨立服務，同一個 repo，只透過 `proto/` 的介面溝通 | [D-01](decisions.md#d-01) |
| 大廳 | 自己寫的薄 Go 大廳；需要社群功能時（M3）再評估 Nakama | [D-02](decisions.md#d-02)、[D-20](decisions.md#d-20) |
| 房間 | Go，每個房間一個 goroutine | [D-01](decisions.md#d-01) |
| 規則 | Node，`goban-engine`（OGS 開源的圍棋規則庫）加 OGS 的死子估算器；無狀態 | [D-04](decisions.md#d-04)、[D-05](decisions.md#d-05)、[D-17](decisions.md#d-17) |
| 服務之間 | gRPC | [D-03](decisions.md#d-03) |
| 玩家連線 | WebSocket，大廳一條、房間一條，進房用入場券 | [D-01](decisions.md#d-01) |
| 前端 | Vue，圍棋棋盤用 `goban`（OGS），先擺子、伺服器為準 | [D-14](decisions.md#d-14) |
| 圍棋終局 | 數子法；系統提出死子判斷，雙方可切換死子後同意；談不攏才恢復對局 | [D-06](decisions.md#d-06)、[D-07](decisions.md#d-07) |

不採用的方案（Colyseus、boardgame.io、NNGS、IGS、OGS 後端）見 [D-02](decisions.md#d-02) 與 [D-16](decisions.md#d-16)。

### M1：能完整下一盤圍棋與五子棋

**實作規格見 [spec_v2.md](spec_v2.md)**（只涵蓋 M1，欄位、階段、錯誤代碼、時限都已定義）。

| 順序 | 工作 | 內容 | 規格 |
| --- | --- | --- | --- |
| 1 | proto 介面 | 大廳 ↔ 房間、房間 → 規則；repo 結構 | [2.2](spec_v1.md#22-程式碼分離)、[第 4 章](spec_v1.md#4-介面) |
| 2 | 規則服務 | 包住 `goban-engine`；加入五子棋模組（沿用三框架 PoC 的規則）；估算器編成 WebAssembly 在 Node 載入；通用階段；提出死子判斷與目數、切換死子；單元測試（提子、打劫、自殺、重放、計分、切換死子） | [第 6 章](spec_v1.md#6-規則服務) |
| 3 | 房間服務 | 房間 goroutine、閘道、送出佇列；驗證入場券；基本重連；先寫紀錄再廣播；呼叫規則服務；通用的「等待雙方同意」處理；保底時限；回報房間事件；用假大廳測試；同一份房間程式跑圍棋與五子棋 | [第 5 章](spec_v1.md#5-房間內部)、[3.3](spec_v1.md#33-入房與重連)、[3.6](spec_v1.md#36-時限與棋鐘) |
| 4 | 大廳 | 訪客登入、`who`、房間列表推送、約局（`match`、`accept`、`decline`、`withdraw`、`pending`）、多房間狀態、`rejoin`、呼叫 `CreateRoom`、簽發入場券、接收房間事件、戰績摘要 | [3.1](spec_v1.md#31-登入與大廳)、[3.2](spec_v1.md#32-約局)、[3.10](spec_v1.md#310-棋譜與戰績) |
| 5 | 前端 | 大廳畫面（玩家、房間、邀請）；五子棋棋盤元件；對局畫面（`goban` 棋盤、先擺子、pass、認輸、切換死子、同意、恢復對局）；重新整理後自動重連 | [3.4](spec_v1.md#34-對局)、[3.5](spec_v1.md#35-終局) |
| 6 | 端對端測試 | 用程式模擬兩位玩家完成一局 | — |

驗收條件：

- [ ] Alice 從大廳邀請 Bob，Bob 接受，雙方用入場券進房。
- [ ] 在 19 路棋盤下完一局：提子、打劫正確，不合法的落子被拒絕。
- [ ] 雙方連續 pass 後，系統提出死子判斷並計分；雙方可點選切換死子，任一方修改後對方的同意作廢；雙方同意後定案。也測一次「談不攏 → 恢復對局 → 再次 pass → 定案」。
- [ ] 認輸可以結束對局。
- [ ] 棋譜完整存在房間服務的資料庫；大廳只有摘要；可以查回整局棋譜。
- [ ] 局結束後雙方回到大廳，房間從列表消失。
- [ ] 對局中重新整理頁面，能用重連憑證回到原座位與目前局面。
- [ ] 接受邀請後有人不進房、終局確認沒人回應、雙方都關掉分頁：房間都會在時限內結束，不留下殘留的房間或「對局中」狀態。
- [ ] 下完一局五子棋（連五獲勝、下滿和局）；房間服務與大廳服務沒有為五子棋寫任何專屬的程式碼，只有規則服務多一個模組、前端多一個棋盤元件（[D-23](decisions.md#d-23)）。
- [ ] 三個服務各自獨立啟動；`lobby/` 與 `room/` 沒有互相 import。

M1 **不做**：棋鐘、悔棋、觀戰、完整的斷線處理（保留座位倒數、跨裝置重連）、開放房間、還價、讓子、五子棋的連珠規則（禁手）、帳號登入。「不做棋鐘」不代表沒有時限：到場、終局確認、斷線、對局總時長等保底時限要做（[spec_v2.md 4.6](spec_v2.md#46-保底時限)）。

### M3：社群功能與帳號

需要好友、私訊、帳號時才開始。

1. 花**最多一週**依 [Nakama 驗證規格](https://github.com/yshsu0918/yi-arena/blob/poc/nakama-lobby-go-room/docs/poc-nakama-lobby-go-room.md) 做驗證，重點是 Nakama 的 Go 擴充能否與 Nakama 本身的 gRPC 套件版本相容，以及能否照同一份 proto 介面和房間服務溝通。
2. 通過：換成 Nakama 大廳，房間服務與規則服務不用改。
3. 不通過：在自己的 Go 大廳上補好友、私訊、登入。

M3 的功能：註冊與登入、個人資料、查詢玩家、好友與上線通知、私訊、封鎖、離線訊息（見 [feature-list.md](feature-list.md) 第 1、12 節）。

## 3. 主要風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| OGS 估算器判死子不準，或無法在 Node 載入 | 自動判死子做不出來或常常要修正 | M1 第 2 步最先處理；雙方可手動切換死子，判錯不會判錯勝負；最壞情況改用「提乾淨再結算」或接 KataGo |
| 房間不小心寫死圍棋的流程 | 加其他遊戲時要改房間程式 | 階段與提案用通用格式；M1 就用同一份房間程式跑圍棋與五子棋 |
| `goban-engine` 的資料格式與動作紀錄對不上 | 規則服務要寫較多轉換 | 規則服務只對外暴露自己的格式，`goban-engine` 包在裡面 |
| 兩個服務之間的事件同步出錯 | 房間列表或玩家狀態錯誤 | 事件帶序號、可重送、定期對帳 |
| 之後要換 Nakama 卻接不上 | 社群功能要自己寫 | M3 只花一週驗證，不通過就自己寫 |
