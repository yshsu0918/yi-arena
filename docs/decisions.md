### D-01

**大廳、房間、規則三分離，第 2 層分離**

- **背景**：目標是自己掌握大廳，並能在不改平台的情況下加新遊戲；之後也可能把大廳換成 Nakama。
- **選項**：
  1. 同一個程式、分 package，直接互相呼叫；
  2. 同一個 repo、三個獨立程式，只透過 proto 介面溝通；
  3. 三個 repo。
- **決定**：選項 2。
- **理由**：
  - 選項 1 換大廳時，房間也得跟著改；`poc/go-lobby` 就是這種寫法，大廳與房間互相持有指標與 channel。
  - 選項 3 修改介面時要跨 repo 同步，成本高。
  - 選項 2 讓房間服務只認介面，自己寫的大廳與 Nakama 大廳對它來說是一樣的。
- **代價**：服務之間要同步事件、對帳、簽發入場券；玩家要連兩條 WebSocket。

### D-02

**大廳先自己寫，不用 Colyseus；Nakama 留到 M3**

- **背景**：三框架 PoC 後曾暫定 Colyseus；之後決定房間用 Go。
- **選項**：Colyseus 大廳、Nakama 大廳、自己寫的 Go 大廳。
- **決定**：先用自己寫的薄 Go 大廳。需要好友、私訊、帳號時（M3），花最多一週驗證 Nakama，通過就換。
- **理由**：
  - **Colyseus**：房間搬到 Go 之後，只剩連線管理與房間列表推送可用，而且沒有好友功能，不值得多一種技術。
  - **Nakama**：社群功能現成，但第一個公開版本用不到（D-20）。主要風險是 Go 擴充引用 gRPC 套件時能否與 Nakama 本身的版本相容。
  - **Go 大廳**：PoC 已證明簡單可行；採 D-01 後，之後換成 Nakama 只影響大廳。
- **證據**：
  - 三框架 PoC 比較：[history/poc-results.md](history/poc-results.md)。
  - Go 大廳 PoC：`poc/go-lobby` 分支的 `docs/poc-go-lobby.md`，100 位模擬使用者全數通過。
  - Nakama 驗證規格：`poc/nakama-lobby-go-room` 分支。

### D-03

**服務之間用 gRPC**

- **選項**：內部 HTTP、gRPC、訊息佇列。
- **決定**：gRPC，大廳 ↔ 房間雙向、房間 → 規則。
- **理由**：介面以 proto 明確定義並產生程式碼，三個服務共用同一份約定（D-01）；Go 與 Node 都有成熟的 gRPC 支援。瀏覽器不走 gRPC。

### D-04

**圍棋規則用 `goban-engine`，放在 Node 規則服務**

- **背景**：房間用 Go，但最成熟的開源圍棋規則庫 `goban-engine`（OGS，Apache-2.0）是 JavaScript。
- **選項**：
  1. Go 自己寫規則，編成 WebAssembly 給前端；
  2. Go 內嵌 JS 引擎（goja）執行 `goban-engine`；
  3. 獨立的 Node 規則服務，房間以 RPC 呼叫；
  4. 前後端各寫一份，以共用測試案例保持一致。
- **決定**：選項 3。
- **理由**：
  - 直接重用 OGS 驗證過的規則與點目流程，前端用同一版 `goban`，前後端規則一致。
  - 選項 1 要自己寫點目流程；選項 2 要確認 goja 能否執行新語法；選項 4 兩份程式碼遲早不一致。
  - 規則藏在 proto 介面後面，之後要換成選項 1 或 2，房間不用改。

### D-05

**規則服務無狀態，每次重放動作紀錄**

- **背景**：圍棋的打劫與 superko 需要完整歷史，不能只看目前盤面。
- **選項**：
  1. 每次帶完整動作紀錄重放；
  2. 在 proto 定義圍棋專屬的精簡狀態（盤面、劫點、歷史盤面 hash）；
  3. 規則服務保存狀態。
- **決定**：選項 1；必要時可加上「不透明狀態」：規則服務回傳、房間原樣保存並帶回，不解讀。
- **理由**：
  - 實測重放成本很低，第一版不需要加速。
  - 選項 2 讓房間認得圍棋的狀態格式，違反 D-10；positional superko 的 hash 列表本身也隨手數變長。
  - 選項 3 讓規則服務當機時遺失狀態，也無法任意擴充成池。
- **證據**：`goban-engine` 8.3.226，19 路約 300 手，「重放 299 手 + 檢查第 300 手」中位數約 7.5 毫秒，最慢約 10 毫秒（2026-10-31 實測）。

### D-06

**終局：自動提案、手動切換死子、雙方同意**

- **選項**：
  1. 不判死子，要求棋手先把死子提乾淨（Tromp-Taylor）；
  2. 系統自動判斷，雙方只能同意或恢復對局；
  3. 系統自動判斷，雙方可手動切換死子再同意；
  4. 雙方完全手動標記（NNGS、IGS 的傳統做法）。
- **決定**：選項 3。
- **理由**：
  - 選項 1 對人類玩家不友善。
  - 選項 2 遇到估算器誤判雙活時，恢復對局再下也解不開，會反覆進入確認又被推翻。
  - 選項 4 流程最長、爭議最多。
  - 選項 3 大多數情況一鍵同意，誤判時可直接修正；`goban-engine` 支援切換死子。
- **規則**：任一方修改，雙方先前的同意全部作廢；談不攏才恢復對局。

### D-07

**數子法；恢復對局照正常輪次；確認時限到視為同意**

- **數子法**：恢復對局、把有爭議的棋下清楚，在數子法下不會改變目數，所以公平；數目法（日本規則）下會改變目數，需要另一套爭議程序。第一版只做數子法。
- **恢復對局照正常輪次**：雙方各 pass 一次才進入確認，各放棄一手，恢復後照常輪流，沒有人能多拿一手。
- **確認時限到視為同意**：不回應只會讓自己接受判斷，故意拖延沒有好處；時限內斷線重連仍可回應。

### D-08

**超時依收到時間判定，計時器帶編號**

- **背景**：最後一秒落子與超時可能同時發生。
- **被否決的做法**：依事件在房間 channel 裡的排隊順序判定。
- **理由**：
  - 落子要先經過閘道才進 channel，計時器則由別的 goroutine 直接送進來，佇列順序不等於實際發生的順序。
  - 房間等待規則服務回應時，事件都在排隊，誰先誰後只是運氣。
  - 舊計時器可能在取消前已觸發，留下過期的事件。
- **決定**：閘道蓋收到時間；用收到時間扣時；計時器事件帶編號，過期的忽略；判超時前先處理已排隊的事件；計時器設在截止時間加寬限之後觸發。
- **參考**：NNGS 每秒掃描一次所有對局，以處理時的時間扣時，誤差在 1 秒內。

### D-09

**不做上線廣播**

- **背景**：Go 大廳 PoC 第一次跑 1,000 位模擬使用者時，每人上線都廣播給所有人，3 秒內產生約 100 萬則訊息，塞爆送出佇列，212 條連線被踢。
- **選項**：逐筆廣播、每 200 毫秒合併後廣播、不廣播（快照加查詢）。
- **決定**：不廣播。登入時給快照，之後用 `who` 查詢。好友的上線通知屬於 M3，只通知相關的人。
- **證據**：改為不廣播後，1,000 人全部連上只要 0.44 秒，沒有連線被踢（`poc/go-lobby` 分支的 `docs/poc-go-lobby.md`）。

### D-10

**階段與提案通用化，房間不寫死遊戲**

- **背景**：圍棋有「連續 pass → 確認死子 → 恢復對局」的專屬流程；若寫死在房間，加五子棋或其他遊戲時就得改房間。
- **決定**：
  - 階段只有 `進行中`、`等待雙方同意`、`已結束`，由規則服務決定。
  - 提案內容房間不解讀，只記錄、廣播、收集同意。
  - 房間服務測試要用一個假遊戲跑過。

### D-11

**棋譜由房間記錄，大廳只存摘要**

- **決定**：房間每接受一個動作就先寫進房間服務的資料庫再廣播；大廳只在局結束時保存摘要；規則服務只轉換格式。兩個服務的資料庫分開、帳號分開。
- **理由**：棋譜是房間的資料，也是房間重啟還原、規則重放、匯出、等級分的共同來源；大廳不應直接讀寫房間的資料表（D-01）。
- **先寫再廣播**：避免出現「大家都看到了、棋譜卻沒記到」的動作。

### D-12

**講評不給棋手看是禮儀，不是防作弊**

- **背景**：NNGS 的 `kibitz` 只送給觀戰者，對局中的棋手收不到。
- **結論**：只要有私訊，或場外通訊（LINE、電話），隔離就擋不住報招。所以講評隔離的目的是讓棋手專心、不被劇透形勢。
- **防作弊**改用事後偵測（以 KataGo 比對著法吻合率）、檢舉，以及重要比賽的嚴格模式（關私訊、延遲直播）。第一版不做防作弊。

### D-13

**保底時限與基本重連放進 M1**

- **背景**：M1 原本排除「計時」與「斷線重連」。
- **問題**：
  - 沒有時限，有人不進房、不確認、或雙方都關掉分頁時，房間永遠不會結束。
  - 沒有重連，前端開發時重新整理一次就回不了房間。
- **決定**：M1 不做棋鐘，但要做到場、確認、全員斷線三種時限，以及憑重連憑證回到原座位。

### D-14

**前端先擺子，伺服器為準**

- **決定**：在 `進行中` 階段輪到自己時，前端用同一版規則庫先檢查並立刻顯示；伺服器拒絕或版本不符時，依伺服器狀態重畫。版本號由房間發。
- **理由**：落子不必等伺服器回應，手感較好；判定仍在伺服器，前端被竄改也不影響結果。
- **限制**：`等待雙方同意` 階段雙方可能同時操作，不先擺，等伺服器回傳。

### D-15

**所有對局預設公開可觀戰**

- **決定**：邀局、開放房間建立的對局，都出現在房間列表，可觀戰。不公開或不開放觀戰之後做成建房選項。

### D-16

**不使用 NNGS、IGS、OGS 的伺服器**

- **NNGS**：2009 年後沒人維護；實測有訪客斷線整盤消失、點目結果錯誤等 bug；只有 telnet 文字協定、只能下圍棋。只當規格參考。
- **IGS**：商業服務，無法自架。
- **OGS**：網頁前端開源（AGPL），後端不公開，無法自架；只使用其 Apache-2.0 的 `goban` 與 `goban-engine`。
- **證據**：[history/nngs-test/](history/nngs-test/README.md)、[history/design-discussion.md](history/design-discussion.md) 5.6、5.7 節。

### D-17

**死子估算用 OGS 估算器，不用內建簡易估算**

- **背景**：`goban-engine` 的自動判死子（`autoscore`）需要搭配「每點歸屬」估算器。
- **選項**：內建簡易估算（Voronoi）、OGS 估算器（`online-go/score-estimator`，MIT，C++）、KataGo。
- **決定**：OGS 估算器，編成 WebAssembly 在規則服務載入。
- **理由**：
  - Voronoi 實測判斷不了死活：一顆被白棋三面包圍的黑子仍判為活棋，白地全部不算。
  - `goban-engine` 內建的估算器載入函式限定只能在瀏覽器執行，但估算器本身是獨立的 C++ 專案，可以另外編譯。
  - KataGo 最準，但需要另外架設服務，留作之後的選項。
- **狀態**：OGS 估算器尚未實測（見「待驗證」）。

### D-18

**時鐘在伺服器，並做延遲補償**

- **決定**：計時與判超時都在伺服器；前端只負責倒數顯示。每手補償估計單程延遲，上限 1 秒；整局上限 30 秒；讀秒歸零後寬限 0.5 秒。斷線不停錶。
- **理由**：前端的時間可被竄改。只用伺服器時間則網路差的人吃虧，所以補償延遲；設上限避免假裝延遲高來偷時間。斷線停錶會讓輸棋的人拔網路線逃避。
- **參考**：NNGS 的時鐘也在伺服器，但沒有延遲補償，斷線即封盤。

### D-19

**悔棋走提案流程，而不是 NNGS 的對手直接撤回**

- **NNGS 的做法**：下錯的一方用聊天請求，由輪到下棋的對手輸入 `undo` 撤回上一手；一次只能撤回 1 手。
- **決定**：請求者送出悔棋請求，對手同意或拒絕；直接落子視為拒絕；撤回 1 或 2 手，依請求時的輪次決定。
- **理由**：有明確的請求介面，對手已回應一手後也能撤回自己的棋；撤回以重放完成，提子與劫的歷史自然正確。

### D-20

**第一個公開版本不做好友與私訊**

- **決定**：好友、私訊、帳號、封鎖、離線訊息放在 M3。
- **影響**：大廳可以先用最薄的版本（D-02）。
