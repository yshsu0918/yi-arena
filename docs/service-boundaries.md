# 服務邊界：切乾淨為什麼難，以及怎麼守住

> 整理日期：2026-11-04。
> 原則見 [decisions.md](decisions.md) 的 D-01、D-10、D-27：**每件事交給擁有那份知識的服務**；大廳、房間、棋譜服務不寫任何遊戲規則，遊戲知識只放在規則服務。

## 1. 規格審查中實際漏出去的地方

幾輪審查找到的問題，幾乎都是同一類：**某個服務不小心知道了不屬於它的東西**。

| 漏掉的地方 | 誰知道了不該知道的 | 怎麼收回來 |
| --- | --- | --- |
| 大廳驗證棋盤路數、貼目，決定黑白 | 大廳知道圍棋規則 | 交給規則服務的 `ValidateSettings`（D-27） |
| 房間檢查座標、輪次，把 `undo` 轉成 `resume` | 房間知道圍棋規則 | 遊戲指令原樣轉給規則服務（D-27） |
| 大廳把 `go` 改寫成 `go_resume` | 大廳知道遊戲名稱 | 由遊戲目錄的 `resume_game` 告訴它（D-41） |
| 開局、斷線規則都寫成「兩位棋手」 | 房間假設遊戲是兩人 | 改看 `traits.seats`（D-42） |
| `sresign` 讓棋譜服務自己重放、產生一盤棋 | 棋譜服務變成會下棋 | 拿掉 `sresign`（D-42） |
| 封盤的棋譜放進 `settings` | 大廳的推送夾帶整盤棋譜 | 改放在 `CreateRoom` 的 `initial_record`（D-42） |
| 登入時呼叫 `Kick` | 大廳插手房間的連線 | 交給房間「同一座位只留最新的連線」（D-41） |

## 2. 為什麼這麼難

1. **方便的寫法通常就是越界的寫法**：「大廳順手檢查一下路數」「房間順手看一下輪到誰」，寫起來最快，但每一個「順手」都是以後要改的地方。
2. **新功能會暴露舊的假設**：加了覆盤房間（1 個座位），才發現房間預設是兩個人；加了續下，才發現大廳得知道遊戲名稱。只用一種遊戲測，這些問題永遠看不到。
3. **乾淨是有代價的**：每把一件事交回給擁有它的服務，就多一個介面（`catalog`、`traits`、`initial_record`……）。切得越乾淨，介面越多。

## 3. 怎麼守住（不必追求完美）

- **把規則寫成可以檢查的條件**：規格已經寫了「`lobby/`、`room/`、`records/` 裡不得出現任何遊戲名稱或遊戲規則」。實作時做成自動檢查，例如在這些目錄的程式碼裡搜尋 `go`、`gomoku`、`komi` 等字，出現就讓測試失敗。
- **一開始就用不同形狀的遊戲來測**：圍棋（2 人、有點目）、五子棋（2 人、沒有點目）、覆盤房間（1 人、不是比賽）。三者差很多，房間只要對其中一個寫了特例，另外兩個就會壞掉。
- **接受少量、有意識的例外**：例如棋鐘在房間服務，其實假設了遊戲有輪流的概念，但它透過規則服務給的 `waiting_on` 決定誰的時鐘在走，已經夠乾淨。不必為了理論上的純粹再多拆一層。
- **遇到「順手」的寫法先問一句**：這份知識屬於哪個服務？如果答案不是自己，就改成向那個服務要，或請它把需要的通用性質放進 `traits`、遊戲目錄。

## 4. 下一步

規格已經過好幾輪審查、大致收斂。剩下的問題多半要寫程式才會出現（時序、效能、`goban-engine` 實際的行為）。照 [roadmap.md](roadmap.md) 的實作順序，先做到第 8 步「能完整下一盤」，同時用圍棋與五子棋驗證；過程中發現越界的地方，回頭補規格，並把它加進第 1 節的表。
