# 壓力測試計畫：大量觀戰

> 整理日期：2026-11-04。狀態：**計畫，尚未執行**。
> 規格見 [spec_v2.md 12.7 節](spec_v2.md#127-觀戰與講評)，相關決策見 [decisions.md](decisions.md)（D-35，以及待驗證的「一個房間 100 位觀戰者」）。

## 1. 目的

1. 用實測數字取代規格裡暫定的「每間最多 100 位觀戰者」（`MAX_OBSERVERS`）。
2. 確認慢連線、大量講評、熱門房間不會拖慢正常的觀戰者與其他房間。
3. 決定 M1 只要調整上限就好，還是需要另外設計「大量觀戰（直播模式）」（feature-list 的「未來」）。

## 2. 測試環境

- 測的是 M1 的房間服務、大廳服務、身分服務（登入）與規則服務，用正式的部署方式（各自獨立的服務與資料庫）。
- 機器人程式沿用 Go 大廳 PoC 的做法（`poc/go-lobby` 分支的 `cmd/bots`），改成走 M1 的介面：註冊登入取得 token → 連大廳 → `observe` → 拿入場券連房間。
- 每次測試記錄機器規格、服務版本、設定值，結果存成 JSON 與文字摘要（比照 PoC 的 `run-100`、`run-1000`）。

## 3. 測試項目

| 編號 | 情境 | 做法 | 指標 | 時機 |
| --- | --- | --- | --- | --- |
| A | 單一房間的觀戰上限 | 一間房，兩個機器人棋手每秒下一手；觀戰機器人依序 100、200、500、1000、2000 人，每一級跑 5 分鐘 | 每手從房間送出到每位觀戰者收到的延遲（中位數、p95、p99、最大值）；房間服務 CPU、記憶體；被斷開的連線數 | 做觀戰時（M1 第二段） |
| B | 慢連線 | A 的每一級裡，10% 的觀戰者故意讀得很慢 | 正常觀戰者的延遲是否變差；慢連線是否照規則被斷開（送出佇列滿） | 同上 |
| C | 講評洪流 | 觀戰者合計每秒送 50、200、1000 則 `kibitz` | 講評推送延遲；落子推送延遲是否受影響 | 有熱門對局需求時 |
| D | 全站 | 50 間房各 100 位觀戰者，加上一間 2000 人的熱門房 | 整台房間服務的總推送量；一般房間的延遲是否被熱門房拖慢 | 同上 |
| E | 進場風暴 | 300 人在 10 秒內同時 `observe` 同一間房 | 大廳發入場券與房間接受 `enter` 的延遲；人數滿時 `observers_full` 是否正確（大廳先擋、房間最後確認） | 同上 |

## 4. 判斷標準

- **可接受**：p99 推送延遲 1 秒以內，沒有正常連線被斷開，房間服務 CPU 不超過 70%。
- 用「仍在可接受範圍內的最大觀戰人數」再打七折，作為 `MAX_OBSERVERS` 的新預設值。

## 5. 結果怎麼用

| 結果 | 決定 |
| --- | --- |
| 單一房間撐到幾千人仍可接受 | M1 直接調高 `MAX_OBSERVERS`，不需要新架構 |
| 幾百人就超出標準 | M1 用測得的安全數字當上限；「大量觀戰」另外設計：房間把局面發佈一次到廣播層，由多台閘道各自推送，搭配延遲直播 |
| 講評先撐不住（C） | 講評加上頻率限制或合併推送 |
| 熱門房拖慢全站（D） | 熱門房要能分到獨立的房間服務實例 |

## 6. 不在本計畫內

- 對局本身的壓力（大量房間同時下棋）、登入與約局的壓力：之後另訂計畫。
- 大量觀戰架構本身的實作：依本計畫的結果決定要不要做。
