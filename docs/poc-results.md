# PoC 結果比較：Nakama、Colyseus、boardgame.io

> 測試日期：2026-10-22。測試計畫見 `docs/poc-test-plan.md`。
> 各分支的程式碼、截圖與詳細說明在 `poc/nakama`、`poc/colyseus`、`poc/boardgameio` 分支的 `test-screenshot/README.md`。

三個分支都完整通過同一套 E2E（19 項檢查，S0～S8）與資料庫驗證（14 項檢查，S9），三者平行執行時也全部通過。三個前端共用同一套 Vue 畫面，只有 `web/src/backend.ts` 依框架不同；E2E 腳本除了埠號外完全相同。

## 各框架的關鍵發現

**Nakama**
- 帳號、聊天（含保存）、儲存、presence 都是內建，自己寫的主要是對局邏輯。
- tick 制：官方建議回合制用 tick 1，但落子要等到下一個 tick，平均約 0.5 秒、最差 1 秒。tick 5～10 延遲就降到 100～200 ms，回合制的伺服器負擔仍然很低。
- 擴充程式碼選 TypeScript（goja，只支援 ES5、不能用 npm 套件）。規則模組因此寫成不依賴任何東西的 ES5 相容程式碼。
- 客戶端陷阱：`matchJoin` 中廣播的第一個狀態可能比 `joinMatch()` 的 promise 先到，要在呼叫前就記下 match id（tick 10 時穩定重現）。
- room 聊天頻道預設任何人知道名稱就能加入，要用 before hook 擋。

**Colyseus**
- 最直接：房間就是一個類別，訊息收到就處理，大廳房間列表是推送的。
- 帳號、積分、聊天、資料庫全部要自己做（這次 PoC 用訪客名稱，沒有驗證）。
- 0.18 的網路範例多半是舊版寫法（套件名稱已改為 `@colyseus/sdk`），需要看型別定義確認 API。
- 玩家列表只在單一程序有效，多程序要接 Redis presence。

**boardgame.io**
- 全員 leave 時比賽連同紀錄從資料庫刪除；已結束的房間只能留在列表上，需要另外做紀錄保存與清理。
- 伺服器拒絕落子不回傳原因；`isConnected` 在多人同時離開時不可靠（推測是 metadata 更新互相覆蓋）。
- 沒有「等人到齊」的概念，要自己加 phase。
- 最後一版 0.50.2，相依套件有 13 個已知漏洞（6 high）。

## 建議

1. **不建議 boardgame.io**：除了研究時已知的維護問題，PoC 又發現紀錄會被刪除、錯誤原因不回傳、連線狀態不可靠，這些都要自己繞過。
2. **Nakama 與 Colyseus 都可行**，差別在「內建多少」：
   - 需要帳號（含社群登入）、好友、排行榜、聊天保存等平台功能時，**Nakama** 省下的工作最多；tick 設 5～10 即可解決延遲問題。
   - 想要最簡單、最即時的對局伺服器，平台功能願意自己做或另找服務時，選 **Colyseus**。
3. 依研究文件的原計畫（Nakama 為主、Colyseus 備案），PoC 沒有發現推翻這個順序的問題。

## 本次 PoC 沒有驗證的項目

- 斷線重連（三個分支都有實作座位保留，但沒有在 E2E 中測試）
- 和局畫面與紀錄（選配項目）
- Nakama 聊天頻道 hook 的拒絕行為（已實作，未自動測試）
- 排行榜、帳號登入（OAuth）、Rapfi 引擎整合
- 多程序／多節點部署
