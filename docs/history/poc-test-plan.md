# PoC 測試計畫：三種框架的大廳與對局（End-to-End）

## 1. 目的

用同一套測試情境，比較三種框架做「線上對弈平台」的實際表現：

| 框架 | 分支（暫定） | 服務埠 |
| --- | --- | --- |
| Nakama | `poc/nakama` | 8901 |
| Colyseus | `poc/colyseus` | 8902 |
| boardgame.io | `poc/boardgameio` | 8903 |

三個框架可以平行開發與測試，細節見 4.1。

每個框架都要完成：大廳、房間、對局、聊天、資料庫紀錄，並以 End-to-End 測試留下截圖作為證據。

## 2. 範圍與假設

- 每個框架都實作**兩種遊戲**：
  1. **井字棋**（3×3，連三）
  2. **五子棋**（15×15，freestyle，連五；無 AI、無禁手）
- 兩種遊戲已確認為井字棋與五子棋。五子棋只做 freestyle，**不含 AI 對戰、不含禁手規則**，本 PoC 只測人人對戰。
- 遊戲規則寫成獨立模組，不依賴任何框架（沿用「大廳管理器」與「遊戲邏輯模組」分層的概念），各分支各自實作一份規則程式碼，規則與測試案例保持一致。
- 前端不求美觀，只要能完成下列流程與畫面即可；**三個 PoC 的前端都用 Vue**。
- 登入方式：**不串 OAuth**，用訪客名稱進入。

## 3. 分支與截圖目錄

- **程式碼放進三個獨立分支**（`poc/nakama`、`poc/colyseus`、`poc/boardgameio`），每個框架一個，只放該框架的程式碼與測試結果。
- 三個分支從**同一個基底 commit**（例如 main）開出，基底只放本計畫文件。
- 遊戲規則模組與 E2E 腳本**各分支各自一份**：三個框架的擴充語言不同（Nakama 用 Go 或 TypeScript，Colyseus 與 boardgame.io 用 TypeScript／JavaScript），規則程式碼也很難直接共用。
- 要同時開發三個分支時，用 `git worktree` 讓三個分支同時檢出在不同資料夾，例如：`git worktree add ../poc-nakama poc/nakama`。
- 截圖存在**該分支**的 `test-screenshot/` 目錄，並提交（commit）進分支。
- 目錄下**不再分框架子資料夾**（分支本身就代表框架）。

```text
test-screenshot/
  README.md                 # 本次測試結果摘要、哪些項目為 N/A
  db-check.txt              # 資料庫驗證的查詢與結果
  01-lobby-initial-p1.png
  ...
```

檔名規則：`<兩位數流水號>-<步驟>-<玩家>.png`，例如 `04-roomlist-waiting-p5.png`。

## 4. 測試環境與工具

- 啟動各框架服務與其資料庫（建議用 Docker Compose），**每次測試前清空資料庫**，確保結果可重現。
- E2E 工具建議使用 **Playwright**：為五位玩家各開一個獨立的瀏覽器 context（獨立的登入狀態），用 `page.screenshot()` 截圖。
- 每位玩家使用不同的身分（例如訪客名稱 `Player1` ～ `Player5`）。
- 畫面截圖使用固定視窗大小（例如 1280×800），方便前後比對。

### 4.1 平行執行與埠號

三個框架可以同時開發與測試，彼此用不同的埠號與資料庫隔離：

| 框架 | 服務埠 | 說明 |
| --- | --- | --- |
| Nakama | 8901 | 把對外服務埠改為 8901（設定方式以官方設定文件為準）；管理後台維持預設即可，只有一個 Nakama 實例，不會與其他框架衝突 |
| Colyseus | 8902 | 遊戲伺服器埠 |
| boardgame.io | 8903 | 遊戲伺服器埠 |

規則：

- 程式與 E2E 測試都從環境變數（例如 `PORT`、`BASE_URL`）取得位址，不要寫死；預設值就是上表的埠號。
- **每個框架使用獨立的資料庫**（獨立容器與埠，或獨立的 database 名稱）。「測試前清空資料庫」只清自己那一份，避免平行時互相影響。資料庫埠也要錯開，避免都用預設的 5432，例如 5441、5442、5443（暫定）。
- Docker Compose 為每個框架指定不同的專案名稱（例如 `docker compose -p poc-nakama up`），避免容器與網路名稱衝突。
- 各分支各自維護一份 E2E 腳本，流程與檢查點相同，`BASE_URL` 預設為該框架的埠（`http://localhost:8901`、`8902`、`8903`）；截圖寫到各自分支工作目錄下的 `test-screenshot/`。
- 平行跑 E2E 時，三組測試會同時開 15 個瀏覽器 context，機器資源不夠就改成輪流執行。

## 5. 測試情境

### 5.1 角色分配

| 玩家 | 角色 |
| --- | --- |
| P1 | 房間 A（井字棋）的房主 |
| P2 | 房間 A（井字棋）的對手 |
| P3 | 房間 B（五子棋）的房主 |
| P4 | 房間 B（五子棋）的對手 |
| P5 | 全程留在大廳的旁觀者：用來驗證玩家列表、房間滿了不能加入、聊天不外洩 |

### 5.2 步驟與截圖檢查點

| 步驟 | 操作 | 驗證 | 截圖 |
| --- | --- | --- | --- |
| S0 | 五位玩家都進入大廳 | 大廳列表可見；房間列表為空；玩家列表顯示 5 人（如果有） | 大廳（P1、P5 視角）：大廳列表、房間列表、玩家列表 |
| S1 | P1 建立井字棋房間 A；P3 建立五子棋房間 B | 房間列表出現 2 個房間，標示遊戲類型與「等待中」；P5 的畫面即時更新 | 房間列表（P5 視角） |
| S2 | P2 從房間列表加入 A；P4 加入 B | 兩個房間人數變為 2/2 | 房間列表（P5 視角）、雙方進房畫面 |
| S3 | P5 嘗試加入已滿的房間 A | 被拒絕，顯示錯誤；A 的對局不受影響 | P5 的錯誤畫面 |
| S4 | 兩個房間的遊戲開始 | 兩個房間各自進入對局畫面；大廳顯示房間為「進行中」；玩家列表顯示玩家狀態（如果有） | **遊戲開始畫面**（P1、P3 視角）、大廳（P5 視角） |
| S5 | 兩房間**同時**輪流落子：井字棋 3～4 步，五子棋 6～8 步 | 輪到誰才能落子；非法落子被拒絕；兩房間互不干擾 | **遊戲中畫面**（A、B 各一張，雙方視角） |
| S6 | 房內聊天：A 房 P1 與 P2 互傳訊息；B 房 P3 與 P4 互傳訊息 | 房內雙方收到對方訊息；A 房的訊息不會出現在 B 房；P5 看不到任何房內訊息 | 聊天畫面（A、B 各一張） |
| S7 | 房間 A：P1 連成三子獲勝；房間 B：P3 連成五子獲勝 | 雙方畫面都顯示正確的勝負 | **遊戲結束畫面**（贏家與輸家視角各一張，A、B 各兩張） |
| S8 | 四位玩家按「返回大廳」 | 玩家回到大廳；房間列表中已結束的房間被移除或標示「已結束」；玩家列表顯示 5 人皆在大廳 | **返回大廳後的大廳列表、房間列表、玩家列表**（P1、P5 視角） |
| S9 | 資料庫驗證（見第 6 節） | 兩場對局都有紀錄且內容正確 | 以 `db-check.txt` 保存（必要時加查詢結果截圖） |

選配（時間允許再做）：

- 追加一場井字棋和局，驗證和局畫面與紀錄。
- 對局中一方斷線再重連，驗證能回到原座位與棋盤。

## 6. 資料庫驗證

每場對局結束後，資料庫中必須有一筆對局紀錄，三個框架使用**相同的欄位**，方便比較：

| 欄位 | 說明 |
| --- | --- |
| game_id | 對局唯一識別 |
| game_type | `tictactoe` 或 `gomoku` |
| players | 兩位玩家的身分與執子順序 |
| moves | 依序的棋步清單 |
| result | 勝者或和局 |
| started_at、ended_at | 開始與結束時間 |

驗證項目：

1. 兩場對局各有一筆紀錄，沒有缺漏也沒有重複。
2. `game_type`、玩家身分、勝負與畫面一致。
3. `moves` 的順序與數量與實際落子一致。
4. 房間 A 的紀錄不含房間 B 的棋步。
5. 把查詢指令與結果存進 `test-screenshot/db-check.txt`。

各框架的寫入方式：

| 框架 | 作法 |
| --- | --- |
| Nakama | 在對局結束時用內建儲存寫入對局紀錄，查詢 Nakama 使用的資料庫（儲存物件的資料表，實際表名以專案為準） |
| Colyseus | 框架不替你保存對局紀錄，PoC 需自行接資料庫（例如 Postgres 或 SQLite），在對局結束時寫入 |
| boardgame.io | 啟用資料庫轉接器（例如 bgio-postgres），查詢對局的 metadata 與 state |

## 7. 聊天驗證

- 房內聊天：同一房間的雙方即時互通訊息。
- 隔離：不同房間、以及留在大廳的 P5，都收不到房內的訊息。
- 結果記錄：框架內建聊天，或需自行實作，要在結果表中註明。
- 選填：聊天紀錄是否保存到資料庫。

## 10. 各框架特別注意

- **Nakama**：對局處理器以 tick 為單位，回合制要設定低 tick 頻率，測試落子延遲是否可接受；擴充程式碼用 Go 或 TypeScript 擇一，並記錄選擇原因。
- **Colyseus**：房間列表用內建 LobbyRoom；玩家列表、聊天紀錄、資料庫都要自己做，記錄各花了多少工。
- **boardgame.io**：預設儲存在記憶體，一定要接資料庫轉接器才能驗證第 6 節；大廳畫面元件是 React 版，前端已定用 Vue，所以大廳畫面要自己做（可直接呼叫它的 Lobby API），並記錄這部分花的工。
