## 1. 要解決的問題

- **規格和討論混在一起**：架構文件裡夾著「為什麼這樣決定」「實驗數字」「和其他方案比較」；設計討論紀錄照時間順序累積，規格散在其中，讀起來像流水帳。
- **沒有明確的功能列表**：現有功能、各階段要做的功能、未來才做的功能，都沒有一份清楚的清單。雖然和 NNGS 比較過，但沒有整理成功能列表。

## 2. 調整後的文件結構

```text
docs/
 ├─ roadmap.md          目標、里程碑、驗收條件（只留結論，理由移到 decisions.md）
 ├─ feature-list.md     功能列表：每個功能的階段與目前狀態，附 NNGS 指令對照（已完成）
 ├─ architecture_v1.md  規格：依功能分章，只寫「系統怎麼運作」
 ├─ decisions.md        討論與決策：每個決定的背景、選項、結論、理由、證據
 └─ history/            不再採用或已完成的內容
```

## 3. architecture_v1.md：純規格，依功能分章

```text
1. 概觀            目標、三個服務、元件圖、名詞
2. 服務與程式碼     各服務的職責、repo 結構與分離規則
3. 功能規格         每個功能一章，與 feature-list.md 的分類一致
4. 介面            大廳↔房間、房間→規則、前端↔大廳、前端↔房間的訊息
5. 房間內部        事件迴圈、計時器、寫紀錄、錯誤隔離
6. 規則服務        分派、通用階段、圍棋（goban-engine、估算器）
7. 資料            棋譜、戰績摘要、資料庫歸屬
8. 故障處理
```

第 3 章的功能章節（對應 feature-list.md）：

| 章節 | 內容 | 里程碑 |
| --- | --- | --- |
| 3.1 登入與大廳 | 訪客登入、玩家列表、房間列表 | M1 |
| 3.2 約局 | 邀請、接受、拒絕、撤回、逾時、還價 | M1、M2 |
| 3.3 入房與重連 | 建房、座位、入場券、重連憑證 | M1、M2 |
| 3.4 對局 | 落子、先擺子、版本號、pass、認輸、對話 | M1 |
| 3.5 終局 | 提案、切換死子、同意、恢復對局、數子法 | M1 |
| 3.6 時限與棋鐘 | 保底時限、棋鐘、超時判定 | M1、M2 |
| 3.7 悔棋 | 請求、同意、限制 | M2 |
| 3.8 觀戰與講評 | 觀戰入場券、講評只給觀戰者 | M2 |
| 3.9 開放房間 | | M2 |
| 3.10 棋譜與戰績 | 記錄、查詢、摘要、SGF | M1、M2 |

每個功能章節使用同一個格式：

- **行為**：條列規則，例如「確認時限到，未回應者視為同意目前提案」。
- **涉及的服務**：誰負責什麼。
- **訊息**：用到哪些介面與訊息（連到第 4 章）。
- **例外**：時限、斷線、錯誤代碼。
- **里程碑**。
- **流程圖**：需要時放在該功能章節裡。

寫法規則：

- 只寫現在式的規格（「房間會……」「必須……」），不寫討論過程。
- 不比較其他方案，不放實驗數字。
- 需要理由時只留一行連結，例如「（理由見 D-08）」。

## 4. decisions.md：討論與決策紀錄（新檔）

一個決定一節，固定格式：**背景 → 考慮過的選項 → 決定 → 理由 → 證據 → 日期**。

| 編號 | 決定 |
| --- | --- |
| D-01 | 三服務分離、第 2 層（同 repo、獨立程式、只靠 proto） |
| D-02 | 大廳先自己寫，不用 Colyseus；Nakama 留到 M3 |
| D-03 | 服務之間用 gRPC |
| D-04 | 規則用 goban-engine，放在 Node 規則服務 |
| D-05 | 規則服務無狀態、每次重放；可選不透明狀態 |
| D-06 | 終局：自動提案 + 手動切換死子 + 雙方同意 |
| D-07 | 數子法；恢復對局照正常輪次；確認時限到視為同意 |
| D-08 | 超時依收到時間判定，計時器帶編號 |
| D-09 | 不做上線廣播，改快照 + 查詢 |
| D-10 | 階段通用化，房間不寫死遊戲 |
| D-11 | 棋譜由房間記錄，大廳只存摘要 |
| D-12 | 聊天隔離是禮儀，不是防作弊 |
| D-13 | 保底時限與基本重連放進 M1 |

最後兩節：**未決事項**、**待驗證的實驗**（含已測到的數字，例如重放 7.5 毫秒、Voronoi 判不了死活）。
