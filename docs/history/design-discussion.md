## 1. 方向：先做出來，再回頭比較

- 架構現階段不是瓶頸：棋類是回合制，一步棋只是一則小訊息，幾千人同時在線用任何一個框架都扛得住。
- 規則模組不依賴框架，PoC 又是三個框架平行做，選錯框架的代價是重寫大廳，不是重做整個平台。
- 「哪個架構好」靠討論很難有結論，先照自己的構想做出來、跑過 E2E，再回頭看 NNGS 的優缺點。
- 上線後很難改、要先想清楚的只有兩件事：
  1. **對局紀錄格式**：PoC 計畫第 6 節已統一欄位，之後可轉成 SGF 等棋譜格式。
  2. **帳號身分**：段位、戰績綁在帳號上。PoC 用訪客名稱，正式版再接登入。
- 另一個觀點：打敗野狐的關鍵可能不在軟體架構，而在於如何讓用戶轉移過來。

## 2. 通用房間引擎與 JSON 遊戲定義

### 2.1 分層

**JSON 適合定義「設定」和「房間要開哪些能力」，不適合定義「規則」本身。** 規則（落子是否合法、提子、勝負、胡牌）仍寫成程式；想用 JSON 描述所有規則，最後會長成一套程式語言（例如學術界的 GDL、Ludii），很難維護。

| 層 | 負責 | 形式 |
| --- | --- | --- |
| 房間引擎（共用） | 座位、輪次、計時、聊天、觀戰、斷線重連、對局紀錄 | 平台程式 |
| 遊戲定義 | 遊戲名稱、人數、可調參數、開哪些能力 | **JSON** |
| 規則模組 | 初始狀態、合法動作、套用動作、判定結果 | 每個遊戲一份程式 |

規則模組實作固定介面（`setup`、`applyAction`、`result`）。新增一種遊戲，多半只需要一份 JSON 加一個規則模組。

### 2.2 遊戲定義範例

```json
{
  "id": "go",
  "name": "圍棋",
  "players": { "min": 2, "max": 2 },
  "rules_module": "go",
  "options": {
    "board_size": { "type": "enum", "values": [9, 13, 19], "default": 19 },
    "komi": { "type": "number", "default": 6.5 },
    "time_control": { "type": "byoyomi", "main": 600, "periods": 3, "period": 30 }
  },
  "capabilities": {
    "record": { "export": ["sgf"] },
    "spectate": true,
    "undo": "opponent_approval",
    "chat": true,
    "rating": true,
    "hidden_information": false
  }
}
```

### 2.3 「譜」是共用能力

棋譜和牌譜的本質相同：**初始狀態 + 依序的動作 + 結果**。平台用統一格式保存，各遊戲再提供轉換器（圍棋輸出 SGF，麻將輸出天鳳格式等）。這和 PoC 計畫第 6 節的 `moves` 欄位一致。

### 2.4 棋類與牌類的根本差異

1. **隱藏資訊**：牌類每人只能看到自己的手牌，引擎要能「依玩家過濾畫面」，觀戰也要決定看不看得到手牌。
2. **隨機性**：牌譜要保存洗牌種子或發牌結果，重播才會一致，伺服器端也要防作弊。

三個框架中，boardgame.io 的設計最接近這個想法（遊戲定義物件、`playerView`、內建動作紀錄）；Nakama 和 Colyseus 要自己做這一層。

## 3. 座位與開局模型（以德州撲克為例）

多人遊戲讓「邀局」變複雜，複雜度主要來自「座位」和「什麼時候開始」。

| 問題 | 圍棋、五子棋 | 德州撲克 |
| --- | --- | --- |
| 人數 | 固定 2 人 | 2～9 人，會變動 |
| 何時開始 | 坐滿就開 | 達到最少人數就開，其他人可陸續加入 |
| 中途加入 | 不行，只能觀戰 | 可以，等下一手牌 |
| 中途離開 | 等於認輸 | 可以離座或暫離（sit out） |
| 一局是什麼 | 一盤棋 | 一手牌；同一張桌子連續打很多手 |
| 開局前協商 | 誰執黑、讓子、貼目 | 盲注大小、買入金額 |

關鍵是把**「桌子」和「一局」分開**：

- **桌子（房間）**：長期存在，管座位、聊天、觀戰。
- **一局（hand／game）**：在桌子上開始、結束，再開下一局；譜以一局為單位保存。

圍棋只是「一張桌子只打一局」的特例。每局開始時，引擎把「這一局有哪些座位參加」交給規則模組，規則模組不用管誰進誰出。

入座方式有三種，由房間引擎統一處理，遊戲 JSON 只宣告支援哪幾種：

1. **開放座位**：建房後掛在房間列表，誰都能坐（PoC 目前測的就是這種）。
2. **指定邀請**：邀請特定玩家，座位保留，逾時取消。
3. **自動配對**：系統依條件（段位、盲注級別）湊人開桌。

```json
// 圍棋
"seating": {
  "seats": 2, "min_to_start": 2,
  "start": "when_full",
  "join_in_progress": false,
  "leave_in_progress": "forfeit",
  "pre_game": ["choose_color", "handicap", "komi"],
  "rounds": "single"
}

// 德州撲克
"seating": {
  "seats": 9, "min_to_start": 2,
  "start": "auto_when_min",
  "join_in_progress": "next_round",
  "leave_in_progress": "sit_out",
  "pre_game": ["buy_in"],
  "rounds": "continuous"
}
```

- 錦標賽（多桌、併桌、盲注升級）是桌子之上的「賽事管理」層，先不做。
- 若要驗證這個模型，PoC 可加一個簡化的多人遊戲（3～4 人、可中途加入）。boardgame.io 的對局人數建房時就固定，Colyseus 和 Nakama 較有彈性。

**目前決定：先只做好圍棋。**

## 4. 圍棋邀局設計

在現有大廳上多加一個「邀請」物件，介於大廳和房間之間。開放座位流程保留，邀局是第二條進房路徑。

### 4.1 流程

```text
P1 在玩家列表點 P2 → 填對局設定 → 送出邀請
        ↓
伺服器檢查：P2 在線、不在對局中、沒有其他待回覆的邀請
        ↓
P2 收到邀請彈窗（顯示設定、60 秒倒數）
   ├─ 接受 → 伺服器建房、兩人直接入座 → 對局開始
   ├─ 修改條件 → 視為拒絕原邀請，改由 P2 向 P1 發出新邀請（見 5.3）
   ├─ 拒絕 → 通知 P1
   └─ 逾時或 P1 取消 → 邀請作廢
```

**房間在接受後才建立**，建好就已坐滿兩人，不會出現在開放房間列表裡被別人搶座。

### 4.2 邀請物件

```json
{
  "invite_id": "inv_123",
  "from": "P1",
  "to": "P2",
  "game_type": "go",
  "settings": {
    "board_size": 19,
    "komi": 6.5,
    "handicap": 0,
    "color": "random",
    "time_control": { "main": 600, "periods": 3, "period": 30 },
    "rated": true
  },
  "status": "pending",
  "expires_at": "2026-10-30T15:01:00Z"
}
```

`status`：`pending` → `accepted` / `declined` / `cancelled` / `expired`。

### 4.3 大廳要補的東西

1. **玩家狀態**：空閒、對局中、離線。只能邀請空閒的人。
2. **個人通知**：伺服器能把訊息推給「某一個人」，不只是廣播。
3. **邀請設定**：「不接受邀請」或「只接受好友邀請」，可晚點做。

### 4.4 邊界情況

- P2 在邀請期間開始別的對局 → 邀請自動作廢。
- 兩人同時互相邀請 → 以先到者為準，後到者作廢。
- P1 在等待中斷線 → 邀請作廢。
- 同一人同時只能發出一個邀請（第一版限制）。
- 所有檢查都在伺服器端做，前端只負責顯示。

### 4.5 三個框架怎麼接

| 框架 | 個人通知 | 接受後建房 |
| --- | --- | --- |
| Nakama | 內建 Notifications，可推給指定玩家（離線也會保存） | RPC 收到「接受」後用 `matchCreate` 建對局，傳入兩人與設定 |
| Colyseus | 在大廳房間對指定玩家的連線送訊息 | `matchMaker.createRoom` 建房，`reserveSeatFor` 替兩人保留座位 |
| boardgame.io | **沒有內建**，要自己架 WebSocket 或在大廳後端加推播 | 呼叫 Lobby API 建對局並幫兩人 join，把 `matchID` 與 credentials 傳給雙方 |

Nakama 最省工（個人通知與線上狀態內建），boardgame.io 最吃力。

## 5. NNGS 參考

### 5.1 基本資訊

- 版本：NNGS 1.1.22（SourceForge 最新版，2009 年）。
- C 語言，約 2.2 萬行，從西洋棋伺服器 FICS 改寫而來；205 個指令。
- 玩家用 telnet 純文字連線，或透過 CGoban 等客戶端。
- 授權：GPL v2 or later。

### 5.2 功能與我們的差距（只看圍棋）

| # | 功能 | NNGS 的做法 | 我們 |
| --- | --- | --- | --- |
| 1 | 約局 | `match 對手 顏色 棋盤 時間 讀秒`；用新條件回發即還價；`pending` 列出、`decline` 拒絕；`open` 標示接受邀請 | 缺，見第 4 節 |
| 2 | 終局點目 | 連續 pass 後標記死子，可 `undo`，`score` 預覽，雙方都 `done` 才定案 | 缺，最花工 |
| 3 | 規則細節 | 讓子、雙方同意才能改貼目、positional superko（三劫循環繼續下） | 缺 |
| 4 | 計時 | 伺服器計時、加拿大讀秒（N 分鐘內下 25 手）、約 1 秒內自動判超時；`addtime`、`pause` | 缺，見第 9 節 |
| 5 | 封盤續下 | `adjourn` 經雙方同意保存，`load` 繼續，保留 10 天，`touch` 延期 | 只有選配的斷線重連 |
| 6 | 悔棋 | 輪到下棋的一方輸入 `undo` 撤回對手上一手（見第 8 節） | 缺，見第 8 節 |
| 7 | 觀戰講評 | 見 5.5 | 缺 |
| 8 | 等級分與紀錄 | 計分／不計分（`free`）、mlrate 等級分、9 路與 19 路天梯、`results` 戰績、SGF | 只有對局紀錄 |
| 9 | 其他模式 | 研究盤（`teach`）、連棋（`pair-go`）、比賽對局（`tmatch`） | 缺 |
| 10 | 社交與管理 | 頻道、私訊、站內信、忙碌狀態、封 IP、過濾髒話、死活題、職業棋譜庫、GMP 電腦棋手 | 大部分不需要 |

**圍棋第一版必做 1～6 項**，其中終局點目最花工，PoC 結束後先做。

我們會比 NNGS 好的地方：網頁與手機可用、規則和大廳分離可擴充其他棋類、用資料庫保存（NNGS 玩家資料一人一個檔案）、連線加密（NNGS 走 telnet，登入時密碼明碼送出）。

### 5.3 可以抽離什麼

**不搬程式碼，只抄設計**：

- 程式綁得太緊：依賴全域陣列 `parray`（玩家）、`garray`（對局），輸出直接寫成 telnet 文字（`pcn_out`）。
- 語言不合：我們用 TypeScript 或 Go。
- 授權：GPL。只在自己伺服器上跑不必公開原始碼，但若散布含有它的程式，整個程式要用 GPL。只抄設計沒有這個問題。

值得抄的設計：

1. **通用「提議」機制**（`pending.h`）：所有需要對方同意的事共用同一種資料結構：

   ```c
   #define PEND_MATCH   0   // 約局
   #define PEND_ADJOURN 1   // 封盤
   #define PEND_PAUSE   2   // 暫停計時
   #define PEND_KOMI    4   // 改貼目
   #define PEND_DONE    5   // 點目完成
   #define PEND_LADDER  6   // 改成天梯對局
   #define PEND_PAIR    7   // 連棋
   struct pending { int type; int whofrom; int whoto; int param1..param5; float float1; };
   ```

   我們可做成房間引擎的共用能力，約局、悔棋、封盤、改貼目、點目確認共用一套流程：

   ```json
   {
     "proposal_id": "p_1",
     "type": "match | adjourn | pause | komi | done | undo",
     "from": "P1", "to": "P2",
     "params": { "board_size": 19, "color": "B", "main_time": 30, "byoyomi": 10 },
     "status": "pending"
   }
   ```

2. **還價方式**（`comproc.c` 約 2888～2940 行）：
   - 乙用相同條件（顏色互補）回發 `match` → 視為接受，立即開局。
   - 乙用不同條件回發 → 自動拒絕甲的提議，改由乙向甲提出。
   - 甲再發不同條件 → 更新自己原本的提議。

   不需要額外的還價狀態。前端可做「接受／拒絕／修改條件」三個按鈕，「修改條件」就是發新邀請。

3. **發邀請前的檢查**（同函式前段）：自己是否在對局中、對方是否在線、是否互相封鎖（censor）、對方是否開放邀請（open）、對方是否在對局中、待回覆邀請數是否達上限。

4. **讓子貼目建議**：依雙方等級分差距建議讓子與貼目，有等級分系統後再做。

### 5.4 大廳怎麼更新

NNGS **沒有定時刷新**。伺服器是事件驅動（`network.c` 主迴圈 `select()`），事件發生時才推送，且由玩家自己訂閱：

| 事件 | 推送給誰 | 訂閱開關 |
| --- | --- | --- |
| 對局開始 | 開啟的線上玩家（不含當事人） | `ginform` |
| 對局結束與結果 | 開啟的玩家與該盤觀戰者 | `ginform` |
| 玩家上線、下線 | 開啟的玩家 | `pinform` |

完整列表（`who`、`games`）由客戶端查詢。模式是：**進大廳時查一次完整列表，之後靠推送事件增量更新**。

我們的做法：

- 進大廳取得完整快照，之後只推送變化（房間新增／更新／移除、玩家上下線與狀態）。
- 不定時輪詢；人多時把一秒內的變化合併成一則訊息。

| 框架 | 房間列表更新方式 |
| --- | --- |
| Colyseus | 內建 LobbyRoom 主動推送增量，最接近 NNGS |
| Nakama | `matchList` 只能查詢，即時更新要自己用 stream 或 notification 推送 |
| boardgame.io | Lobby API 是 REST，只能輪詢（React 大廳元件預設約 2 秒一次，**未查證**） |

這會影響 PoC 步驟 S1「P5 的畫面即時更新」，要記進結果表。

### 5.5 觀戰與講評

- `observe` 觀戰，一人最多同時看 10 盤（`MAX_OBSERVE 10`），不能觀看自己的對局。
- 每手棋即時推送給觀戰者（`gamedb.c` 的 `send_go_boards`）。
- `all` 列出觀戰者；對局結束後觀戰者自動離開。

| 指令 | 誰說 | 誰聽得到 | 存進棋譜 |
| --- | --- | --- | --- |
| `say` | 棋手 | 對手 | 是 |
| `kibitz` | 觀戰者（棋手也能用） | **只有觀戰者** | 是 |

`com_kibitz`（`comproc.c` 約 1480 行起）只把訊息送給觀戰者，**對局中的棋手收不到**；研究盤（`teach`）例外。比賽對局（`tmatch`）另外擋掉他人對棋手的私訊。

### 5.6 實測結果（2026-10-30）

實際編譯並執行 NNGS 1.1.22，用腳本模擬 7 位訪客測試。步驟、腳本與完整紀錄見 [`nngs-test/`](nngs-test/README.md)。

- **編譯**：mlrate 已找不到下載，改用空殼停用等級分；新版 gcc 要加 `-std=gnu89 -fcommon`；安裝路徑要手動修；SIGTERM 關不掉。
- **與讀原始碼一致**：約局與還價、輪流檢查、觀戰即時推送、講評只給觀戰者、`say` 只給對手、悔棋由對手直接撤回、約 1 分鐘內自動判超時、SGF 自動存檔（含講評與對話，不含被撤回的棋步）。
- **發現的問題**：
  1. 訪客斷線後對局自動封盤但不保存，重連後無法續下，這盤等於消失。
  2. 點目結果錯誤：黑方的地沒計入，按完成後卻顯示「黑方認輸」。
  3. `time` 顯示的剩餘時間與棋盤上不一致。
  4. 黑方時鐘在開局時就開始走，不是從第一手開始。

### 5.7 不採用 NNGS 與其他圍棋伺服器的理由

**NNGS**：

1. **沒人維護，也沒有可接手的後繼版本**：最後一版 2009 年，公開伺服器約 2005 年關閉；沒找到還在維護的開源分支（GitHub 上只有棋譜封存）。
2. **現在要跑起來就得手動修補**（見 5.6）。
3. **實測有 bug**：訪客斷線整盤消失、點目錯誤、時間顯示不一致。
4. **接不上網頁**：只有 telnet 純文字協定，要另寫 WebSocket 閘道並解析文字輸出；連線沒加密，密碼明碼傳送。
5. **只能下圍棋**：圍棋寫死在程式各處，無法做通用房間引擎與 JSON 遊戲定義。
6. **設計不符合需求**：只有加拿大讀秒；沒有延遲補償；斷線就封盤，計分對局可拔線逃避；悔棋沒有請求流程。
7. **技術債與授權**：C 語言、全域陣列、資料存成檔案；GPL，散布修改版要公開原始碼；2002 年郵件列表提到 IGS 主張協定受著作權保護並認為 NNGS 侵權，沿用協定可能有法律風險。

**同一系或同類的伺服器**：

| 方案 | 能自己架嗎 | 說明 | 可以借用什麼 |
| --- | --- | --- | --- |
| IGS（Pandanet） | 不能 | 日本 NKB 公司經營的商業服務；沒找到伺服器原始碼；協定只有舊版文件公開 | 無 |
| WING | 不能 | 日本的圍棋伺服器，搜尋沒找到公開原始碼 | 無 |
| OGS（online-go.com） | 不能 | 網頁前端開源（AGPL v3），**後端不公開**（論壇說法：程式太亂、且是維護者主要收入） | `goban` 規則庫（Apache-2.0，OGS 前後端共用）、前端介面參考 |

- OGS 前端是 AGPL：照抄程式碼，我們的前端也必須用 AGPL 並公開原始碼，所以只參考介面設計。
- OGS 的 `goban` 授權寬鬆、在 OGS 實際運作，經比較後列為首選規則庫（見第 7 節）。

**結論**：NNGS 當規格參考，其餘方案都無法自架；自己做是唯一能完全掌握的路線。

## 6. 聊天隔離與防作弊

- 只要有私信（`tell`），觀戰講評的隔離就擋不住報招；就算關掉私信，場外通訊（LINE、微信、電話）平台也管不到。
- 結論：**聊天隔離是禮儀設計，不是安全機制**。目的是讓棋手專心、不被劇透形勢。
- 設計：
  1. 觀戰講評預設不顯示給棋手，對局結束後公開並存進棋譜；棋手可設定「對局中不接收私信」。
  2. 防作弊靠事後偵測：用 KataGo 比對著法與 AI 首選的吻合率，異常者標記並人工審查；加上檢舉機制。
  3. 有獎金或計分的比賽再加嚴格模式：關私信、關觀戰，或延遲數手直播。
  4. **第一版不做防作弊**。

## 8. 悔棋設計

### 8.1 NNGS 的做法（`gameproc.c` 的 `com_undo`，約 990 行起）

NNGS 的悔棋**不走提議機制**，而是「由對手動手撤回」：

- 下錯的一方用聊天請求，**輪到下棋的一方**（也就是對手）輸入 `undo`，撤回上一手。
- 不是輪到你下就不能 `undo`（研究盤與點目階段例外）。
- 一般對局一次只撤回 1 手；研究盤可以 `undo 5` 一次撤回多手。
- 點目階段 `undo` 會回到對局狀態，並取消雙方的「完成」確認。
- 撤回時通知雙方與所有觀戰者；同時取消該玩家所有待回覆的提議。

優點是不需要「請求、同意」兩步。缺點是請求只能靠聊天，介面不直覺，而且對手已經回應一手後就沒辦法撤回自己的棋。

### 8.2 我們的做法：走通用提議機制

```text
P1 按「悔棋」→ 送出 undo 提議（type: "undo"）
        ↓
P2 看到「對手請求悔棋」
   ├─ 同意 → 撤回、輪到 P1、通知觀戰者
   ├─ 拒絕 → 通知 P1，P1 在下一手之前不能再請求
   └─ P2 直接落子 → 視為拒絕
```

撤回幾手，看請求時輪到誰：

| 請求時機 | 撤回 | 撤回後輪到 |
| --- | --- | --- |
| P1 剛下完，P2 還沒下 | 1 手（P1 的） | P1 |
| P2 已經回應一手，輪到 P1 | 2 手（P2 的和 P1 的） | P1 |

不接受撤回超過 2 手的請求（研究盤除外）。

### 8.3 規則

- **同時只能有一個悔棋請求**；被拒絕後，要等請求者再下一手才能再請求，避免洗版。
- **計時**：請求期間時鐘照走，不暫停、不退還時間。輪到誰下就扣誰的時間，對手若不想等可以直接落子（等於拒絕）。
- **點目階段**：同意悔棋會回到對局狀態，清除已標記的死子與雙方「完成」確認。
- **次數限制**：每局上限由遊戲設定決定。
- **計分對局**：預設不允許悔棋，或限制次數，由設定決定。
- **觀戰者**：收到「第 N 手已撤回」的通知，畫面同步更新。
- **研究盤**：不需要同意，可一次撤回多手。

### 8.4 遊戲定義（JSON）

```json
"undo": {
  "mode": "opponent_approval",   // none | opponent_approval | free（研究盤）
  "max_plies": 2,
  "max_per_game": 3,
  "allow_in_rated": false,
  "allow_in_scoring": true
}
```

### 8.5 實作注意

- **用棋步紀錄重建盤面**：撤回時不要「拿掉棋子」，而是從初始狀態重放剩下的棋步。提子、劫和 superko 的歷史會自動正確，規則模組只需要支援重放。
- **紀錄保留完整事件**：資料庫保存所有事件（落子、悔棋請求、同意、拒絕），方便事後查爭議；匯出 SGF 時只輸出最終的主線棋步，被撤回的棋步可以選擇存成變化圖。
- **所有判斷在伺服器端**：誰能請求、撤回幾手、次數是否用完，都由伺服器檢查。

## 9. 計時設計

### 9.1 NNGS 的做法（`gameproc.c` 的 `game_update_time`，約 2197 行起）

- **時鐘在伺服器**：時間單位是 0.1 秒（`TICSPERSEC 10`）。每盤記錄雙方剩餘時間（`ticksleft`）和上次扣時的時刻（`lastDectick`）。
- **兩個時間點扣時**：
  1. **收到落子時**：先扣掉這手用的時間，再換對方（`gameproc.c` 約 521 行）。用的是「伺服器收到的時刻」，網路延遲也算進玩家的時間，**沒有延遲補償**。
  2. **定期掃描**：主迴圈的 `select()` 最多等 1 秒，每次醒來都呼叫 `process_heartbeat` → `game_update_times()`，掃描所有進行中的對局並扣時。所以就算沒人落子，超時也會在大約 1 秒內被發現。
- **自動判超時**：讀秒中剩不到 1 秒就由伺服器判負（`END_FLAG`）。`time` 指令只是立刻強制更新一次並顯示時間，不是必要的確認步驟。
- **加拿大讀秒**：
  - 基本時間用完不會判負，而是自動進入讀秒，並通知雙方「進入讀秒，剩 N 手、M 分鐘」。
  - 讀秒中每下一手，剩餘手數減 1；手數歸零就重置成新的讀秒時段（時間和手數都回滿）。
  - 讀秒時間用完、手數還沒下完 → 判負。
- **客戶端顯示**：每次推送棋盤時附上雙方剩餘時間和讀秒手數，客戶端自己倒數。
- **不計時對局**：可以下不計時的對局；研究盤也不計時。
- **點目階段停錶**。
- **暫停**：`pause` 走提議機制（`PEND_PAUSE`），雙方同意才停錶，`unpause` 恢復。
- **加時**：`addtime` 送時間給對手。
- **斷線**：玩家斷線時，對局自動封盤（`command.c` 約 1110 行，`END_LOSTCONNECTION`），之後用 `load` 續下。
- **續下保護**：`load` 時若有一方剩不到 30 秒，自動停錶，等雙方 `unpause`。

### 9.2 時鐘放哪裡：伺服器為準，客戶端只負責顯示

**判定一定要在伺服器**。客戶端的程式和時間都能被竄改，例如改掉倒數、暫停自己的時鐘，所以不能用客戶端的時間判定超時。

| 位置 | 負責 |
| --- | --- |
| 伺服器 | 保存剩餘時間、扣時、判定超時、補償延遲 |
| 客戶端 | 本地倒數顯示、讀秒提示音；每次收到伺服器訊息就校正 |

伺服器每次推送狀態時，附上「雙方剩餘時間」和「這段時間從哪一刻開始算」。客戶端據此在本地倒數，畫面流暢，但最終以伺服器為準。

### 9.3 網路延遲怎麼算

只用伺服器計時，延遲會算進玩家的時間：從伺服器送出「輪到你」，到收到你的落子，中間的網路來回都被扣掉。網路差的人會吃虧，讀秒時尤其明顯。

建議的補償方式：

1. **伺服器量延遲**：每隔幾秒 ping 每位玩家，估計單程延遲。
2. **每手補償**：扣時 = 伺服器量到的時間 − min(估計延遲, 上限)。上限例如每手 1 秒。
3. **每局補償上限**：整局累計補償有上限（例如 30 秒），避免有人假裝延遲很高來偷時間。
4. **讀秒寬限**：讀秒歸零後再給一點寬限（例如 0.5 秒），伺服器收到才判定超時。

印象中 lichess 用類似做法（伺服器時鐘加延遲補償配額），採用前可再查證細節。

**為什麼不讓客戶端回報「我想了幾秒」？** 因為客戶端可以謊報。若要採用客戶端回報，也只能當參考，必須用伺服器量到的時間設上下限。

### 9.4 計時方式（遊戲 JSON 設定）

```json
"time_control": {
  "type": "byoyomi",          // none | absolute | fischer | byoyomi | canadian
  "main": 600,                // 基本時間（秒）
  "periods": 3,               // 讀秒次數（byoyomi）
  "period": 30,               // 每次讀秒秒數
  "stones": 25,               // 加拿大讀秒：每時段要下的手數
  "increment": 0              // fischer：每手加秒
}
```

- **日式讀秒（byoyomi）**：基本時間用完後，每手要在 N 秒內下完；超過就用掉一次讀秒，用完判負。華人圈和野狐常見（例如保留時間加 3 次 30 秒），**第一版先做這種**。
- **加拿大讀秒**：NNGS 用的方式。
- **Fischer 加秒**、**包乾（absolute）**：之後再加。

### 9.5 規則

- **伺服器主動判定超時**：在對方時間用完（加寬限）的時刻設一個計時器觸發判定。NNGS 是每秒掃描所有對局，效果類似，但對局多時計時器比較省。
- **斷線不停錶**：斷線時時鐘照走，否則輸棋的人可以拔網路線逃避。給斷線者在時間內重連；時間用完就判超時負。不計分對局可以改成像 NNGS 一樣自動封盤。
- **點目階段停錶**，但點目本身要有時限（例如 3 分鐘），避免一方拖延不按「完成」。
- **暫停**：走提議機制，雙方同意才停錶；計分對局不允許或限制次數。
- **悔棋**：不退還時間（見第 8 節）。
- **讓子擺放**：自由擺讓子時，擺子期間不計時。

### 9.6 紀錄與測試

- **每手記錄用時**：資料庫保存每手用了幾秒、補償了多少延遲。可匯出成 SGF 的 `BL`／`WL`（剩餘時間）屬性，也能用來分析作弊（例如每手用時異常規律）。
- **E2E 測試**：
  - 用很短的計時設定（例如基本時間 0、讀秒 1 次 5 秒）測超時判負。
  - 用 Playwright 搭配 Chrome DevTools Protocol 模擬網路延遲，驗證延遲補償。
  - 測斷線後時鐘繼續走，以及重連後時間正確。

### 9.7 獨立計時模組

多種遊戲都需要計時，所以計時要和規則模組一樣做成**獨立模組**，不依賴任何框架或遊戲。

在架構中的位置：

| 層 | 和計時的關係 |
| --- | --- |
| 規則模組 | **完全不碰時鐘**，只告訴引擎「下一個輪到誰」 |
| 房間引擎 | 持有一個時鐘，每次換手呼叫時鐘；依時鐘給的截止時刻設計時器 |
| 計時模組 | 純計算：扣時、讀秒、判定超時，不知道網路和遊戲規則 |
| 框架轉接層 | 提供計時器：Colyseus 用 `clock.setTimeout`；Nakama 在每個 tick 檢查（低 tick 頻率約 1 秒內發現，和 NNGS 一樣）；boardgame.io 印象中沒有內建伺服器端計時器，要自己補（未查證） |

設計原則：

1. **純函式、注入時間**：所有操作都傳入 `now`，模組自己不讀系統時間、不設計時器。好處是單元測試不用真的等待，幾毫秒就能跑完「讀秒用完判負」這類情境。
2. **延遲補償由外部傳入**：網路層量出延遲，換手時把 `lagCreditMs` 傳進來；模組只負責套用上限（每手上限、整局上限）。
3. **不假設兩人**：用座位編號，支援 N 人；也不假設輪流，換手時由引擎指定下一個座位。
4. **可序列化**：狀態能轉成 JSON 存進資料庫，伺服器重啟或封盤續下時可以還原。
5. **吐出事件**：進入讀秒、用掉一次讀秒、超時等事件由模組回傳，引擎決定怎麼通知玩家和寫紀錄。

介面草稿（TypeScript）：

```ts
type Seat = number;

interface ClockConfig {
  type: "none" | "absolute" | "fischer" | "byoyomi" | "canadian";
  mainMs: number;
  periods?: number;        // 日式讀秒次數
  periodMs?: number;       // 每次讀秒時間
  stones?: number;         // 加拿大讀秒每時段手數
  incrementMs?: number;    // Fischer 每手加秒
  graceMs?: number;        // 超時寬限
  maxLagCreditPerMoveMs?: number;
  maxLagCreditPerGameMs?: number;
}

type ClockEvent =
  | { type: "entered_overtime"; seat: Seat }
  | { type: "period_used"; seat: Seat; periodsLeft: number }
  | { type: "timeout"; seat: Seat };

interface Clock {
  start(seat: Seat, now: number): void;
  // 目前的人走完一步，換下一個座位；回傳這手用時與事件
  switchTo(next: Seat, now: number, lagCreditMs?: number): { usedMs: number; events: ClockEvent[] };
  pause(now: number): void;
  resume(now: number): void;
  addTime(seat: Seat, ms: number): void;
  // 若沒有人行動，目前的人會在哪個時刻超時；引擎用它設計時器
  nextDeadline(): number | null;
  // 檢查是否已超時（計時器觸發或定期掃描時呼叫）
  check(now: number): ClockEvent[];
  // 給客戶端顯示用：各座位剩餘時間、讀秒次數、正在走的座位、伺服器時刻
  snapshot(now: number): ClockSnapshot;
  toJSON(): ClockState;
}
```

各種遊戲的對應：

| 遊戲 | 計時方式 |
| --- | --- |
| 圍棋 | 日式讀秒（第一版）、加拿大讀秒 |
| 五子棋 | 包乾或日式讀秒 |
| 西洋棋類 | Fischer 加秒 |
| 德州撲克 | 每次行動限時，超過後扣「時間銀行」；可以看成「先用讀秒、再用基本時間」的變形，之後再加一種類型 |

程式碼共用：PoC 計畫規定各分支各自一份程式碼。不過 Colyseus、boardgame.io 和選用 TypeScript 的 Nakama 都能直接用同一份 TypeScript 計時模組。PoC 之後若決定共用，可以抽成獨立套件。

## 10. 框架決定：暫定採用 Colyseus（2026-10-30）

> **已被取代**（2026-10-31）：改為自己寫的薄 Go 大廳、Go 房間服務、Node 規則服務，三者以 gRPC 溝通。見 [roadmap.md](../roadmap.md)。以下保留當時的比較作為紀錄。

依據 `poc/nakama` 與 `poc/colyseus` 兩個分支的實測（兩者 E2E 19 項、資料庫 14 項皆全數通過），暫定採用 Colyseus。

| 比較 | Colyseus | Nakama |
| --- | --- | --- |
| 執行環境 | 一般 Node.js，可用 npm 套件、`async`、計時器 | TypeScript 只支援 ES5、不能用 npm 套件、沒有非同步；或改用 Go 外掛 |
| 落子延遲（點擊到畫面出現） | 下棋者約 50 ms、對手約 24 ms | tick 1 約 879 ms、tick 5 約 190 ms、tick 10 約 89 ms |
| 房間列表即時更新 | 內建推送（`LobbyRoom`） | 只能輪詢 |
| 大廳設計自由度 | 高，房間以外都自己設計 | 中，要配合它的對局、通知、頻道模型 |
| 部署 | Node 程式 + PostgreSQL | Nakama + PostgreSQL（PoC 另加 nginx） |
| 帳號、好友、私訊、聊天紀錄、排行榜 | **都要自己做** | 內建 |
| 人工開發粗估（PoC 範圍） | 1～1.5 天 | 1.5～2 天 |

採用理由：

1. 符合「自己的大廳管理器」的目標：房間以外的運作方式（邀局、提議機制、玩家狀態）都能照本文件的設計做。
2. 可直接使用 OGS 的 `goban-engine`（見第 7 節），省下點目流程、各國規則與 superko 的實作。
3. 訊息收到就處理，計時可直接用計時器，不必依賴 tick。

已知代價與對策：

- 帳號、好友、私訊、排行榜要自己做 → 第一版不做好友、私訊、等級分與排行榜，但保存完整對局紀錄與 `rated` 欄位，之後可從紀錄重算等級分。
- 多台伺服器時，玩家列表等共享狀態要接 Redis → 第一版單一程序即可。
- 0.18 版文件與網路範例多為舊版寫法 → 以套件型別定義為準。
- 身分驗證要自己做（`onAuth` 驗證 token）。

架構圖與「邀請對局到結束對局」的流程見 [舊版草案](architecture-colyseus.md)。
